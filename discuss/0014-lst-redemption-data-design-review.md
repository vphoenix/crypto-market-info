## 首版边界与复杂度

限定 Ethereum、Lido stETH/wstETH、一个 ETHUSDT USDT 线性永续及两条固定买入路径，适合用公开数据先筛盈利空间。一个 Go 命令、两个有界轮询循环、现有证据归档及 ClickHouse 批写足够，不需要通用协议框架、任务平台、全链索引、NFT 二级市场或自动交易。

七张定类型小表不是当前的过度工程化来源。不同事件、协议状态、金额报价、实际资金费和提交控制有各自身份与完整性语义；合并成通用 JSON 或大量可变标签反而难以核验。固定数量的后续同量报价可放入现有 quote 表，不增加影子账户或交易表。

## 初审发现与最小修正

### P1-1：固定 USDT 金额档不能替代旧敞口的期末退出与平仓报价

同一档位每分钟产生不同的 LST/ETH 数量，因此后来分钟的“100k 买入档对应退出”不是之前某次入场数量的期末报价。未来基差和链上兑现价格均未知，不能用入场当刻反向报价或邻近金额档计算历史完整周期收益。

最小修正有两种：首版明确只给占款/退出成本情景，不报告完整周期净利；或每天只选一个固定时点、轮换路线的已知数量样本，有限保存 +1/3/7/14/30 日同量退出与同量平仓报价。后者只需现有 quote 表中的角色、入场引用、原数量、计划时刻及真实取得时刻。它仍是等待期情景，不代表自己的请求已完成、实际取得了报价或完成了套利。

### P1-2：mark/index 与资金费结算 mark 不能沿用交易 tick

交易所的标记/指数价格精度可能细于交易价格最小 tick。按交易 tick 除后取整会改变保证金估值和资金费现金额；要求整除则会误拒合法来源。

最小修正：盘口仍按 instrument 交易 tick/qty lot；mark、index、资金费结算 mark 使用独立固定 1e-8 USDT 整数单位或足够精确的 Decimal，scale 写入 manifest。未知或超精度不能静默截断。正资金费对 ETHUSDT 空仓为收入，按每次实际结算 mark 与当时空仓 ETH 数量计算，不能累计费率后乘入场名义额。

### P1-3：30 日边界与未完成请求不能被完成者样本掩盖

只统计窗口内已经领取或完成的请求，会排除最近/长等待请求，使排队时间看起来更短。窗口内的 finalization/claim 也可能对应窗口之前创建的请求，缺少起点不能当作零等待或丢进同一完整分布。

最小修正：以窗口内请求为 cohort，request→finalized 与 finalized→claim 分开；未 finalized 为右删失。窗口外起点或未匹配事件单独报告左侧边界/未知覆盖，不拼出假持续时间；没有连续日志覆盖不能宣布“未完成”。分位数未被可观测完成事件识别时标 unknown，报告完成比例、删失比例及按请求数/金额的口径。历史等待只是当前等待情景的依据，不是承诺。

### P1-4：经典 Curve stETH 池的输入是原生 ETH，不能省略资产转换

如果固定白名单选用经典 stETH 池，路径需要 USDT→WETH→unwrap→ETH→stETH。以同 wei 数量调用 get_dy 能取得报价，不意味着 WETH 可以直接支付该池，也不意味着无需 unwrap、approval 或初始 gas ETH。

最小修正：按实际 coins/ABI 核验输入输出身份，路径显式表示 unwrap/wrap、批准和首笔 gas 储备。所有初始资产来自 USDT 或明确资金储备情景，不能假设已有免费 ETH。完整成交及 gas 尚未证明时只标 quoted/indicative，不标 executable。

### P2-1：保证金、手续费和维持保证金只需保守情景，但不能默认为已验证规则

无账户授权时，不接需要签名的专属手续费/杠杆档接口。可以先用显式公开等级/人工核验 manifest 和保守保证金情景；来源未知时输出盈亏平衡手续费及保证金敏感性，不填零。对冲 short 的开平价差、资金费、价格上涨追加现金、lot 残差、领取缩水及分链资金占用须分开。

### P2-2：来源新鲜度与完整性阈值须可检查

源时刻、请求开始、收到和解析完成时间已在草案要求，正式稿还应冻结年龄/时间差上限及预算。Binance REST depth 的 E、T、lastUpdateId 应留存；成功空日志和失败须区分。达到 RPC 已知条数上限或疑似截断应二分，不用“JSON 成功”替代完整性。延迟或缺失不能用旧报价回填。

### P1-5：未知成员的 DDL 不能强迫填造链锚点与来源请求时间

正式正文要求 head/source 失败仍保存固定 1 条 protocol 和 8 条 unknown quote，错过或跳过的 followup 也要记录；但第一份 DDL 中 protocol 的 block_number/hash/time 与协议、报价的所有链请求/收到/可用时间均非 NULL。head 未取得时没有真实锚点，未请求时没有真实请求时刻，网络失败时也可能没有完整响应收到时刻。用零 hash、epoch 0 或本地计划时间补齐会违背正文未知语义。

最小修正：相关链锚点和来源请求/收到/可用字段允许 NULL；保留非 NULL 的本地开始、观测分类和行 available_at。capture 的 received_at 也应允许没有源响应。校验要求状态为 known/完整时必有真实锚点与来源证据，失效时理由明确。只改字段与不变量，不加表。

## 已核验且应保留的协议约束

- Lido 请求记录同时包含 stETH 与 shares。wstETH 必须通过合约换算并保留整数舍入，不按 1 wstETH=1 ETH；两条路线争用同一赎回权利，金额档及重复时间点均是替代选择。
- `WithdrawalsFinalized` 覆盖 `(from,to]`，事件只有总锁 ETH、烧 shares 和 timestamp，**没有 maxShareRate**。不能按总额均摊逐请求，也不能从批次比例倒推出精确兑付。实际 `WithdrawalClaimed.amountOfETH` 可验证已领取请求；未领取为未知，抽样读取 getClaimableEther 必须知道 finalized/claimed 状态，因为 0 也可能表示已领取。
- 进入官方队列后不会继续取得质押收益；名义赎回额存在下行可能。排队期收益不能同时算作 stETH APY 与 funding 收入。
- 领取人的拖延不等于协议排队；request→finalized、finalized→claim、领取后稳定币退出至少应分别表述。
- latest 同 hash 报价应保留 head/finality 状态，历史最终性 revision 后再筛选 canonical，不能让旧分支复活。重试保持内容和批次身份；原始可见时间不被补采或最终性更新刷新。

核验来源：[Lido WithdrawalQueueERC721](https://docs.lido.fi/contracts/withdrawal-queue-erc721/)、[Lido v4.0.1 队列源代码](https://github.com/lidofinance/core/blob/v4.0.1/contracts/0.8.9/WithdrawalQueueBase.sol)、[Binance 官方市场数据文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)。初审以官方 master 交叉检查，复审另读取了 manifest 固定的 v4.0.1 原文；源码归档仍不是当前代理实现证明，正式实现必须做设计要求的启动核验。

### 原设计的遗漏

1. **P1：并发和 batch 数量没有约束实际发出速率。** “最多两个在途”“历史一片一片”“串行 gate”仍可能在低延迟来源上连续高速发送；20 成员 RPC batch 也可能同时送入 20 个方法调用。30 日及额外上下文、事件 header、收据与重试都需要进入统一额度。
2. **P1：启动恢复和限流后的继续请求缺少完整边界。** 未明确 watch 是否会自动回补、积压是否一次补跑、不同 mode 是否共享额度，以及 429/418 后能否被其他任务或重启绕过。核验脚本原先遇 HTTPError 后继续下一项，同 host 后续请求可能违反限流退避。
3. **P2：独立进程 gate 不等于出口 IP 限额。** 现有 collector、其他研究进程及人工核验可能共用出口；本研究自身流量小也不能证明该 IP 有剩余额度。

### 已核对的最小修正

- watch 首次只建立当前 finalized 观察起点，历史 30 日及额外上下文由显式 backfill 执行。所有 LST mode 共用固定状态目录和单一进程排他锁，mode 不是锁键；先读本地游标、种子和冷却状态，超时旧报价不补造。
- 初始化实际 RPC 方法调用至少相隔两秒，启动满一分钟且身份核验完成后才进入常态；初始化时不并行开启历史、收据和市场任务，核验后重新取当前 head。官方 ABI 固定随程序，不每次启动抓代码仓库。
- 关闭多成员 JSON-RPC batch；所有实际调用，包括探测、header、transaction/receipt、finality、报价、分页及重试，都进入发出 gate。常态 RPC 上限两次/秒及 120 次/滚动分钟，最多两个在途；Quoter 另有一秒间隔。显式 backfill 总 RPC 上限一次/秒及 60 次/滚动分钟。发出前重新检查节拍，空闲不积攒突发额度。
- watch 的 getLogs 最多四次/五分钟；显式 backfill 最多 30 次/滚动五分钟且至少相隔十秒。这是刻意不同的两项配额，两种 mode 不并跑。父片、失败片、二分子片均计数；429/超时不触发立即二分。必要 header 未完成不推进连续游标，重复块/交易有缓存。
- Binance 所有 REST 至少相隔五秒，串行、最多 12 请求及 60 权重/滚动分钟；资金费接口组再限制为两次/滚动分钟及十次/滚动五分钟。depth 从 100 降至 10 档，与首版读取范围一致；depth 加带 symbol 的 premiumIndex 常态约三权重/分钟。
- 429/明确限流停止该 host 的本程序请求，至少冷却五分钟并遵守更长 Retry-After，重复限流继续延长；418 或明确封禁/拒绝访问的 403 持久停用。5xx/网络错误低频退避，重试进入同 gate；市场截止后不继续追齐。发出额度、冷却和下次允许时间在发出前原子保存，状态不能保存时停止请求，数据库写入重试不重抓源数据。
- 市场预算仍是 30 秒，优先完整 100k 档；限速与来源延迟使其不能完成时保存 partial/unknown，不提高速率、不放宽时效、不沿用旧 head/quote。finality 核验分批最多四个锚点/分钟，未核验仍是 head/safe，只有真实确认 canonical 且已 finalized 才提升；原可见时间不变。
- 核验脚本仍是八个串行计划请求，无自动重试；同 host 至少五秒，depth 取十档，HTTP403/418/429 归档失败后立即终止整个脚本，不再发后续请求。此次静态核对没有执行脚本的公共网络路径。

官方规则交叉核验：[Binance 市场接口权重](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)、[出口 IP 限流与封禁规则](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/general-info)。RPC 配额是本研究的保守默认配置，没有被当成 PublicNode 或其他供应商的可保证额度。

### 剩余限制与结论

设计中的 gate、持久冷却、排他、滚动计数和公平恢复尚未实现，不能表述为生产程序已经具备这些保护。两次/秒并不能保证全部八档在 30 秒内完成；正文允许部分档缺失，实施需先以本地假时钟/HTTP/RPC 验证所有发送路径，再低速检查实际来源能力。不能通过放宽新鲜度或 finality 来凑完整率。

核验脚本的节拍是单次执行内的状态，尚不跨进程持久化，也不与 LST 或其他 collector 共用 gate；它只适合人工一次性验证，不应放入定时反复执行或自动重启流程。现有其他来源进程的总出口流量仍是部署前检查项，本设计没有改动它们；响应头使用量监测可以暂停本研究，不能暂停外部进程或承诺整个 IP 免封。
