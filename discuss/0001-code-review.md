## 发现的问题

### 1. 阻断：OKX 正常订阅成功响应被当成失败

位置：`internal/exchange/okx/runtime.go:154-164`、`internal/exchange/okx/runtime_test.go:29`

OKX 官方的订阅成功响应包含 `event: "subscribe"`，通常不包含 `code`；`code` 是错误响应的可选字段。当前代码只有在 `code == "0"` 时才接受订阅，因此收到真实成功响应时 `code` 会解析为空字符串，随后连接被判错并反复重连。默认配置下，OKX 现货和永续都无法进入有效盘口状态。

现有测试人为加入了官方成功响应中没有的 `"code":"0"`，所以测试通过但没有覆盖真实协议格式。官方示例见 [OKX WebSocket Subscribe](https://www.okx.com/docs-v5/en/#websocket-api-public-channel-order-book-channel)。

最小修改建议：成功条件按 `event == "subscribe"` 判断；仅对 `event == "error"` 或明确的非成功错误码报错。测试改用官方成功响应形状（不含 `code`）。

### 2. 重要：OKX 序列号维护重置后会永久保存陈旧盘口

位置：`internal/exchange/okx/collector.go:42-50`

OKX 说明维护期间可能发送 `seqId < prevSeqId` 的增量消息，表示序列号被重置。当前代码先执行 `seqId <= lastSeqId` 并直接忽略消息，后面的断档检查不会运行；重置后的后续小序列号也会一直被忽略。

WebSocket 仍在持续收消息，所以静默超时不会触发；内存盘口会保持 `valid`，采样器可能持续把重置前的陈旧盘口写成有效数据。

最小修改建议：在“旧消息忽略”之前识别 `seqId < prevSeqId` 或其他重置关系，立即将盘口置为无效并重新订阅取得快照；增加维护重置回归测试。

### 3. 重要：实际资金费率超过 3 分钟才可用时，估算值不会再被纠正

位置：`internal/funding/scheduler.go:37-46`

调度器只在每个整点后的 3 分钟内重复查询当前整点的实际值。若交易所历史接口延迟超过 3 分钟，或这段时间查询失败，数据库会保留估算值。进入下一小时后，程序只查询新的整点，不再回查上一整点，因此连续运行时该估算值可能永久保留。

这与 `docs/market-data-storage.md` 中“随后取得实际值时，用实际值覆盖估算值”的规则不一致。

最小修改建议：每小时同时回查仍可能是估算值的最近结算整点；无需引入任务队列或新表。增加“实际值延迟到 3 分钟后出现”的调度测试。
