# 2026-10-19 凌晨期权积压回溯

用户明确要求分析查出问题时的状态。本报告聚焦 00:40–03:00，特别是 01:00–02:15；午间恢复不作为故障不存在的依据。本轮没有改变程序、参数、服务或队列。

结论：当时最需要处理的是共享写入链路吞吐下降，期权积压是其主要表现。进入量没有增加；磁盘等待、内存换页、元数据与分钟写入的锁竞争，以及 Redis 慢响应对调度和 ACK 的阻塞共同降低完成速度。不是仅凭“期权数据多”或“Redis 重写很久”就能完整解释。

## 进入量稳定，完成量下降

从已有 writer 日志的累计指标作差。下列速率包括主 collector 的 CEX 和期权批次，不包含直接写入的独立低频服务；各窗口端点以 `log-analysis.json` 的实际指标时间为准。

| UTC+8 窗口 | 新发现批次/分钟 | 完成交付批次/分钟 | 总待处理起止 |
|---|---:|---:|---:|
| 00:40–01:00 | 95.09 | 94.39 | 7→21 |
| 01:00–02:00 | 94.66 | 69.26 | 15→1,535 |
| 02:00–02:15 | 95.73 | 93.43 | 1,502→1,536 |
| 02:15–03:00 | 95.78 | 129.46 | 1,510→0 |

故障小时少完成约 25.4 批/分钟，对应增加 1,520 批，足以解释积压增长。故障前每分钟约 90 批期权、不到 5 批 CEX，因此同一写入链路变慢时，积压主要落在期权。02:37:32 首次重新观测到旧待处理为零，不能把这个恢复结果倒推成 01:00–02:00 没有问题。

`committed_batches` 是通过 MySQL 提交核验并完成必要 ACK 后才增长的计数。“待处理”并不严格等于每一批的业务事实都未写入；ACK 失败也会保留交付。不能把速率直接当作纯 SQL 插入吞吐。

## MySQL 执行和保护锁均变慢

以下为成功完成期权批次的平均耗时，单位毫秒；失败尝试不包含在这些逐批均值中，累计指标另存于证据。

| 环节 | 00:40–01:00 | 01:00–02:00 | 02:15–03:00 |
|---|---:|---:|---:|
| 准备 | 141.7 | 258.1 | 136.7 |
| 获取 producer 保护锁的查询 | 209.0 | 357.5 | 128.1 |
| SQL 事务主体 | 292.0 | 538.9 | 230.9 |
| 事务提交 | 48.0 | 64.0 | 61.6 |
| 提交后核验/清理 ACK 阶段 | 64.0 | 147.8 | 50.1 |

锁阶段也包括该查询本身的 I/O 和执行时间，不能将 357.5 ms 全部解释成纯行锁等待。故障小时另有 26 次查询执行超时和 11 次锁等待超时的交付重试记录，支持链路确实受阻，而非只有统计口径变化。

代码中存在跨任务阻塞路径：

- `internal/storage/mysql/prepared_delivery.go:303`：分钟提交对同一 `producer_generation` 行取 `FOR SHARE`，并持有至事务结束。
- `internal/storage/mysql/discovery.go:140`、`:398`：`beginDiscoveryIntents` 与 `WriteDiscoveryFacts` 进入普通 `transaction`；`producer.go:75`、`:89` 默认取 `FOR UPDATE`。
- 因此同属 collector 的元数据事务持有排他保护锁时，分钟写入不能同时取得该行的共享锁。独立 Reserve/LST 使用各自 producer 行，停止它们不会解除 collector 内部的这条竞争路径。锁语义参见 [MySQL 官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

01:00–02:00，以上两类元数据操作有 331 条慢事务日志，持锁后的事务主体与提交累计 **767.913 秒**。这里排除了它们等待获得锁的时间；仅统计满足慢日志阈值的记录，不代表完整持锁总量，也不是量出了期权被它们阻塞的精确秒数。结合代码，它们是明确会放大磁盘停顿的竞争来源；未保留故障小时逐时刻锁等待图，不能声称每一次期权锁等待都已归因到某一具体事务。

它们说明存储延迟是瓶颈的重要部分；尚不能仅凭全机十分钟统计确定 01:00 是哪个进程或哪次操作首先触发换页/读取升高，也不能把每次 I/O 延迟全部归因于 swap。宿主虚拟机后端盘是否有额外停顿仍未有直接证据。

## Redis 慢响应还会阻塞调度和完成交付

`internal/storage/writer/engine.go:575` 在调度主循环同步调用 Redis `CandidatePage`，给它 3 秒超时预算。故障小时该步骤有 92 条超时/期限错误日志；慢响应期间主循环不能继续分派任务和处理完成事件。这个预算不是严格保证每次调用实际只耗时 3 秒，底层连接超时与重试也会影响它。

`engine.go:337` 起的两个提交工作线程，在 MySQL 提交后还同步执行提交证明查询、spool ACK 和 Redis ACK，然后才接下一批。期权 ACK 平均从 64.0 ms 上升到 147.8 ms，单批最高 **19.51 秒**；ACK 包含数据库核验、spool 文件/目录同步和 Redis 操作，不能把全部 ACK 耗时都记到 Redis。Redis 租约续期失败还会取消交付尝试、产生重试。

现场记录的 **883 秒 AOF 重写约在 01:56 开始、02:10:47 结束**，而积压从 01:00 左右已出现。因此这一次重写是后续加重因素，不能用它解释最初一小时全部吞吐下降。参见 [Redis 官方延迟诊断](https://redis.io/docs/latest/management/optimization/latency/)以及[当时现场记录](io-recheck-20261019.md)。

## 改进应针对阻塞传播

优先评估缩小元数据事务对分钟写入的排他范围，并将 Redis 候选发现、提交后的副本确认从调度/提交关键路径隔离。后者必须保留 MySQL 提交证明、租约与副本可恢复性，不能提前删除未验证数据；前者必须保持 producer fencing、规则/计划和发布顺序不变量，不能直接把所有锁改成共享锁。

同时治理数据库热点内存的换页及宿主存储延迟。已有 Redis 无损压缩候选可减少持久化开销；期权质量字段共享可降低长期写入量，但它们不能代替解决这次确认的阻塞路径。单纯清队列、增加 writer 线程或改新旧任务权重，都没有消除故障期间处理速度低于输入速度的原因。
