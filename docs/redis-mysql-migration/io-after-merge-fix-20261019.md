这是写入链路的登记/校验读取，并非只有用户执行历史查询才会发生。仓库 `internal/storage/mysql/schema.sql` 中，前四张表使用 `_key_hash` 或 `(_key_hash,_occurrence)` 为主键；`publication_prefetch.go` 会按哈希访问主键，`discovery.go` 在发布前读取已有记录并核对内容。InnoDB 用主键组织行数据，哈希分布使新记录和查找目标分散到较多页，是值得验证的随机 I/O 来源。[MySQL 聚簇索引说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

## 后续优先级

1. **针对慢读验证登记表访问方式。** 在隔离库用同一批分钟输入比较当前布局与紧凑、较连续的行布局，保留哈希检索和全部 `_occurrence`、内容冲突、首次获知时间、原子发布语义。计入辅助索引和总写入，不能简单取消重复校验或凭 Redis 未命中判定数据库不存在。若相同块设备在低业务负荷下依旧有数十至上百毫秒读取，再核查宿主机存储，避免只在应用内调整。
2. **减少质量证据的重复物理写入。** 沿用[10 月 16 日原型](io-reduction-20261016.md)：仅目录证据的共享字段有明确逻辑压缩潜力；盘口质量整组共享已证明不合适。做新旧结构同输入对照，测业务文件、redo、doublewrite 合计及回放时间；不重写全部历史，不减少原始精度或有效性证据。
3. **Redis 排在 MySQL 之后。** 它本轮约 1.47 MiB/s，优化其交付/预览值的无损编码值得单独评估，但不能解决 MySQL 文件写入和随机慢读的大头。本轮没有 Redis 持久化状态，不能断言此窗口是否发生 AOF 重写。

doublewrite 本轮有明确写入成本，但它承担恢复保护，不作为直接关闭的建议。已有刷盘参数试验没有稳定收益，不重复将“降低某参数”当成已验证方案。任何结构改造须以同样的输入、充分刷盘后的总 I/O、提交延迟和精确回放验收，不能承诺固定下降比例。
