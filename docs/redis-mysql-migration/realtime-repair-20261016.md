## 修复内容

1. **收益写入失败。** 七个历史收益来源重复返回相同 `observation_time`，但采集时间和来源摘要变化，原 MySQL 不可变行检查会整批拒绝。改为按 `collected_at` 单调刷新：旧批次不覆盖新值，同版本异内容冲突仍整批回滚，已知链锚点及最终性不能倒退。另四个来源的派生利率、兑换比例或 TVL 超过 18 位小数，在收益模型入口采用明确的十进制截断与前后校验，保留来源响应摘要。详见[数据模型](../market-data-storage.md)。不放松通用 codec，不改变收益与资金费的语义。
2. **期权规则刷新阻塞实时分钟写入。** 原不可变规则批次持有 `producer_generation FOR UPDATE`，现场一次事务持续约 23 秒，会阻塞分钟 writer 的共享锁。仅该不可变规则路径改为共享代次锁；全部 SQL 分块仍在一个事务中提交，同键争用需回滚并完整比较，producer 激活仍使用独占锁。可变元数据/计划发布仍保留原协议，未增加 writer 并发或数据库资源预算。
3. **OKX 重连惩罚不重置。** 已有心跳和安静盘口处理正常；现场包含上游异常 EOF。修复连接已收到全部有效快照并运行至少一个最大退避周期后，下一次重连从基础等待重新开始。连续快速失败仍指数退避，连接门控不变，断开立即使盘口失效，新快照和序列连续性检查保留。新增日志字段 `retry_base_ms`。这会缩短恢复等待，不能消除外部断线。
4. **LST 历史日志追赶慢。** 当前生产为 range 模式、显式起点，原先复用了 receipts 的 8 区块上限。range 显式段上限改为 32，已有游标每次成功只增一，范围/时间预算错误仍缩片，不跳过未核验区块；receipts 仍为 8。原 RPC/日志额度、冷却、市场采样频率、来源端点及链锚点核验保留。
5. **目录失败放大为期权采集停顿。** 跨周期复核于 18:59 发现 `markScopeUnknown` 对每个成员又遍历其所在分片的全部成员，把一次 32 成员的失效通知放大为 1,024 条，超过单分片 256 条 ingress 容量；混合范围分片还会错误通知其他范围的成员。改为只检查当前拥有成员的 scope，每个受影响成员发送一次通知。保留立即失效、确认代次屏障、真实队列满时的停止保护，不扩大队列、不丢弃真实源更新。

LST 每轮只调度一条 entry、其余条目显式记为 `not_scheduled`，因此 `status=partial` 不能单独用作失败指标；应同时看 `scheduled_entry`、`usable_entry`、链锚点和 freshness。真实 Binance HTTP 超时仍会使本轮 hedge 未知，不延长陈旧数据的有效期，不删除限流冷却，也不把缺失数据伪装成成功。
