## 结论

本项目 MySQL/Redis 仍是持续磁盘负荷的主体。质量表降写入已生效，平均写入量没有回升；剩余尖峰主要表现为每分钟封口的集中读写、来源登记表的慢随机读，以及几乎每分钟一次的 Redis AOF 重写。另有一组尖峰叠加 Codex 缺页读取和系统换入。不能将所有尖峰都归于单一进程或 AOF 重写。

这两分钟平均忙碌率 45.18%，约一秒区间最高 93.61%，4 个区间超过 90%，14 个区间超过 80%。样本没有抓到 100%，不能否认样本之外发生过满负荷。

本次可对应的 MySQL 文件读取共 47.52 MiB，其中下列三张主库表占 **29.34 MiB / 61.74%**。按读取字节数除以次数计算，平均每次读取为 8 KiB：

| --- | ---: | ---: |
| `public_observation_provenance` | 1,510 | 16.71 ms |
| `source_batch_status` | 1,234 | 19.91 ms |
| `source_publication_intents` | 1,011 | 18.89 ms |

`cex_book_minute_commit` 另有 490 次 8 KiB 读取，平均 28.37 ms。来源登记表用于记录来源证明、发布意图与已发布状态；它们被 CEX/公开发现数据链路复用，不是只服务期权质量表。代码中的这几张表以哈希键组织，事实写入前还要查找、核验原身份和来源记录，访问分散的历史页；事务外预读已经存在，但预读本身仍可能需要真实读盘。

20:56:07 的一秒区间，整盘读仅 **0.223 MiB/s**、写 2.912 MiB/s，忙碌率却为 **88.81%**；平均读请求耗时 **118.24 ms**，写请求仅 0.50 ms。20:57:09 也出现读 0.273 MiB/s、平均读耗时 88 ms、忙碌率 90.11%。同期读取主要来自 mysqld。这说明不能只靠减少 MB/s 判断尖峰是否消失。

文件快照间隔约 30 秒，不能把某一个一秒峰值精确分摊给其中一张表；以上表级归因是整个采样窗口的结果。

## 2. Redis 几乎每分钟重写一次 AOF

实际配置为最小 64 MiB、增长 100% 触发自动重写，保留 `appendfsync=everysec`、`no-appendfsync-on-rewrite=no`。Docker 持久化日志确认：

| 自动重写开始 | 成功结束 | 触发日志 |
| --- | --- | --- |
| 20:55:14.093 | 20:55:14.519 | 100% growth；开始于本次采样之前 |
| 20:56:05.084 | 20:56:05.833 | 107% growth |
| 20:57:05.091 | 20:57:06.641 | 102% growth |

后两次重写与每分钟新数据封口重叠。Redis 在对应十秒区间的写计数分别约 **6.65 / 7.97 MiB/s**，其余大部分十秒区间约 0.3–0.4 MiB/s。现有期权 Redis 交付保存原定类型成员 payload，尚未采用本轮 MySQL 的共享质量物理格式或队列值压缩。

重写是成功且较短的后台任务，不是此前持续十多分钟的故障重写。部分最高磁盘尖峰出现在它结束后，不能据此宣称 AOF 是所有高负载的唯一原因。实时读取的 `aof_delayed_fsync` 是历史累计值，没有采样起点，不能当作本次新增失败数。

按分钟内位置分组：前 20 秒平均忙碌率 **66.39%**，其余时间 **34.21%**；Redis 相应写入约 **3.87 / 0.40 MiB/s**。样本仅覆盖两次分钟封口，但周期集中已在两次都出现。

## 3. 最高一组尖峰还叠加了缺页读取

20:55:21–20:55:24 附近，Codex 进程出现明显缺页读取；其中 20:55:22 的区间为整盘最高 93.61%，Codex 读约 1.20 MiB/s、MySQL 读约 0.52 MiB/s。同期系统存在换入，整个样本换入 **8.51 MiB**，换出为零。

随后只读核验时 MySQL 仍有约 494 MiB、该 Codex 进程约 114 MiB 内存位于 swap。宿主机可用内存约 3.1 GiB；不能据已有 swap 数量推断当前正在持续内存耗尽，也不能仅凭 major fault 将每个进程的全部读取都算作 swap。

ClickHouse 本次进程写入为零，读取仅 12 KiB，12 次合并快照均为空。Reserve/LST 继续 inactive、PID=0。

## 后续处理优先级

1. **先降低 Redis 重写频率并做对照。** 提高自动重写门槛，验证写入峰值、AOF 大小和重启回放时间；保留 AOF、每秒同步及现有交付确认。随后评估期权队列成员的无损压缩，减少初始追加和重写的数据量。不能仅关闭持久化来获得低 I/O。
2. **针对三张来源登记表减少随机页访问。** 对真实输入比较更紧凑的定类型键和记录、按时间集中布局与必要窄索引的总成本，兼顾现有批量/预读路径。保留原来源身份、首次知晓时间、重试冲突核验与事务发布语义；不能直接取消核验，或认为换成 INSERT 就必然无需读取索引页。
3. **单独评估换入干扰。** 优先检查活跃工作集和并行程序内存占用，不直接扩大 MySQL buffer pool 或强制 swapoff；本次没有持续换出，尚无证据支持这类全局调整。

本轮为诊断，以上建议尚未应用。
