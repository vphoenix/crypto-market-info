## 这次还存在写入之外的延迟

02:10:30 的进程状态显示 MySQL 约 **512 MiB**、Redis 主进程约 **95 MiB** 内存位于 swap。MySQL 容器 swap 使用约 511.6 MiB、上限 512 MiB；没有 OOM 或触碰物理内存上限的事件。宿主机仍有约 3 GiB available，不能把已换出的内存等同于此刻全机没有可用内存。

短时 `vmstat` 的三段有效样本持续有约 218–392 KiB/s 换入，没有同期换出。Redis 后台重写进程也有约 47 MiB 已换出内存；读取这些页需要随机磁盘 I/O。[Redis 官方延迟诊断](https://redis.io/docs/latest/management/optimization/latency/)明确说明了 swap 和 AOF 同步写入造成延迟的机制。

Redis 一次 AOF 重写本轮最终自行结束，耗时 **883 秒（14 分 43 秒）**，上一次为 70 秒；AOF 延迟 fsync 计数在文件观测窗口增加 4。采样过程中，连只读 `INFO memory` 也出现一次超过 6 秒的响应超时，导致计划五分钟的联合采样提前结束；已保存的完整采样仍可用，不能把它写成完整五分钟验收。另一个一分钟 `iostat` 窗口出现十秒区间平均写等待 **518.9 ms**、平均读等待最高 **135.52 ms**，说明存在短时严重停顿。

这些证据确认数据库正在承受慢 I/O、换页和持久化延迟；尚未证明所有延迟都由 swap 单独造成，也未定位虚拟机宿主存储层是否另有瓶颈。设备在虚拟机中标记 ROTA=1，不能据此直接断言真实后端一定是机械盘。

## 下一步应针对的问题

1. 优先治理 MySQL、Redis 的内存换页与持久化停顿：核验持续内存峰值和宿主磁盘延迟，再制定进程内存保护和换页策略。当前不能盲目增大 buffer pool，也不应把全机关闭 swap 当成已验证修复。
2. 对已研究但未上线的 Redis 期权 payload/预览无损压缩做真实 AOF 对照，并在压缩后评估重写阈值。它针对反复落盘的字节及重写开销，不改变采样频率与交付保证。
3. 如继续降写入，重点试验主库期权质量证据中重复字段的共享存储；先在隔离库验证物理写入、恢复和历史兼容。本次不以停止其他低频服务替代这项优化，也不承诺质量表压缩比例能等比例变成整盘收益。
