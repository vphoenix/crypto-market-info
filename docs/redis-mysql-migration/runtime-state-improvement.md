# 采集运行状态与历史读取改进方案

2026-10-14（UTC+8）。设计交付，尚未实施。本轮不修改程序、表结构、服务或生产数据。

目标：**程序运行中直接维护自己的进度和待办；正常循环不再从历史采集表重建状态。** 历史记录用于追溯、具体事实核验和明确的恢复操作。改进不减少采集范围，不跳过缺口、完整性或链上最终性检查。

本方案补充[新采集写入积压改进方案](write-backlog-improvement.md)，两者共同服从[存储与交付协议](storage-design.md)。已有方案负责写入积压、Keeper 查询止损和提交效率；本方案负责采集器的状态所有权、增量维护和恢复。以已有方案完成第一步的止损为前提推进，不等待本方案实施才处理长查询。

## 1. 已确认的问题与边界

2026-10-14 的[磁盘诊断](../../research/2026-10-14-disk-write-audit/remaining-load-092951Z/analysis.json)发现，MySQL 在一个采样分钟占虚拟机物理读取量约 87%、写入量约 43%；后续窗口比例变化。这证明新程序的存储访问是重要负荷来源，不能据此认定 Windows 的全部磁盘忙碌都来自本项目，也不能承诺改造后固定降低多少。

代码核对如下。工作区存在其他 Agent 的修改，下面是设计时的代码行为，不等同于全部已部署版本。

| 路径 | 当前行为 | 改造要求 |
| --- | --- | --- |
| Across `runner.go` 的 `Watch` | 内存已有 `captures` 和链游标，仍每约 30 秒重新加载当前 manifest 的 capture 清单 | 使用本进程已确认的增量更新 |
| Across `maintenanceLoop` | 每轮或定时刷新重新读取 capture；`worker()` 创建独立 Collector，未共享一份明确归属的运行状态 | 网络 worker 保留独立证据缓冲，运行状态交给一个管理者 |
| Across `history.go:refreshRepairReceipts` | 除清单外，还通过 `visitRecoveryBatches` 回读相关已提交事件、成交、退款、收据等明细，重建收据待办 | 在新批次提交时从手中已有对象生成待办，不再周期性遍历历史明细 |
| Reserve `runner.go:Reconcile` | 读取当前及 related manifests 全部 capture，再挑未最终确认记录和 finalized 哨兵 | 维护未确认集合及每个适用范围的最终确认锚点 |
| Reserve `recovery.go:RepairReceipts` | 读取清单，按 capture 选择最新尝试，再找待补收据 | 维护保留原筛选语义的待补集合 |
| LST `finalizePending`、`GasPass` | 先读 manifest 的 capture 清单再筛选；GasPass 还读取候选历史批次 | 增量维护待确认记录和原 gas 规则所需候选；这一项有代码证据，尚未单独测得物理 I/O 占比 |
| LST 启动恢复 | `restoreFollowups`、日志游标恢复等根据历史重建状态 | 首次转换后使用经过核验的 checkpoint 和必要尾部恢复 |
| Keeper `advanceEvidence` | 已有 `EventCursors`、`EvidenceCursors`、`Ops`、`Scans`，仍回查数据库核验窗口与子任务完成情况 | 保留已有慢查询修复，再将正常推进改为由已提交结果驱动 |
| MySQL `capture_pages.go` | 每页 500 条，循环直到读取全部匹配历史 | 分页限制单次返回量，不能代替限制整个任务的读取范围 |

`across_capture`、`reserve_capture` 等是持续增长的历史采集登记表，包含范围、摘要、完整性、版本、最终性等，并非只有一行当前状态的小表。本方案也不把它们描述为全部盘口事实表。

以下读取仍然有独立用途：按准确身份验证写入冲突、读取某项待办所需的具体事实、确认结果未知的提交、获取外部链状态、人工报告及历史迁移。它们不能因为“不读历史恢复日常状态”而被一并删除。

## 2. 设计选择

采用 **进程内状态 + 本地持久 checkpoint + 尚未纳入 checkpoint 的恢复记录**。首版不新增 MySQL 状态表，不新增 Redis 状态库，不引入另一套消息服务。

Keeper、LST 已有持久状态和 pending 格式，优先扩展其现有协议；Across、Reserve 补齐必要的运行状态持久化。通用代码只负责原子文件替换、校验、版本和恢复记录边界；各领域保留定类型状态，不做通用 JSON 状态大表或无差别事件总线。

```text
公开来源 → worker 获取、严格解析和冻结结果
                       ↓
              持久保存尚待确认的操作
                       ↓
           原 MySQL 事务及完整性校验
                       ↓ 提交成功或按身份确认成功
              状态管理者应用一次结果
               ├─ 推进连续进度
               ├─ 增加、修订或完成待办
               └─ 合并保存 checkpoint

重启 → checkpoint + 未覆盖操作 → 按身份核验少量提交 → 恢复运行
```

运行中的状态不是历史表副本。只保留：

1. 已连续完成的覆盖边界和必要的缺口区间，原始事件覆盖、解码覆盖、收据覆盖分开表示。
2. 未提交、结果未知、待补、待确认、尚未结束的跟踪任务，以及其稳定身份和必要引用。
3. 当前分支的区块高度、哈希、最终性和必要 finalized 哨兵；必要时保留不同 manifest 的独立锚点。
4. 来源冷却、预算、分页链和重试时间；它们继续遵守原模型，不因新版本重置。
5. 最小的规则身份、提交摘要和恢复版本，不装入全部已结束任务或历史业务 payload。

数据保存多久由语义决定：未完成任务不能因超过一分钟、一天或缓存上限而消失；已完成且后续不再依赖的工作状态可以压缩、移除。LST 的 31 天 followup 等业务窗口保持原规则。状态保存期限与 Redis 当前/上一分钟的盘口缓存期限无关。

## 3. 运行时状态所有权

每个 collector 服务有一个状态管理者，是本服务运行状态的唯一修改入口。网络 worker 可以并行，但只能领取带身份的任务、执行并返回不可变结果；不各自保存并刷新完整 `captures` 副本。

对 Across 保留 Reader 的独立成员/证据缓冲、来源配额以及 probe 的实时优先级。状态管理者不能在锁内等待 RPC、SQL 或 fsync；通过有界任务/结果通道与 worker 协作，按序应用结果。不得把全部网络工作串成一个慢循环。

领域事件包括 `CaptureCommitted`、`RevisionCommitted`、`ReceiptCompleted`、`WindowVerified` 等。字段至少包含服务与配置范围、操作身份、当前 producer 身份、原批次/修订身份、摘要和必要领域数据。只为本方案需要的事件定义定类型结构，不把完整历史记录塞进事件。

规则如下：

- 同一任务最多一个在途执行。通知重复按操作身份和修订去重，内容不同报告冲突。
- 状态管理者为本地操作分配不复用的序号，连同状态世代一起持久保存。checkpoint 记录连续已应用边界及未决例外，压缩已结束操作的去重信息；不能为去重而永久保留每次历史操作的内存对象。该序号只是本地恢复顺序，不替代批次身份、区块顺序或业务连续性。
- 不能按消息到达顺序、最大区块号、最大时间戳直接推进连续游标；先确认前序覆盖和父子依赖。乱序完成的结果保留为待连接区间。
- 对可修订状态携带预期旧 revision；旧结果不能覆盖更新的 canonical/finality。现有存储方法对过时修订可能成功返回但不执行更新，管理者不得因此把旧值装回内存；必要时按准确主键读取当前修订。
- worker 获得的状态是只读视图或副本，不能共享并修改 map/slice。通知通道满时停止分派受影响的新工作或等待有界接纳；不得静默丢弃已提交通知。
- 已持久的未决操作在通知丢失或进程崩溃后可以重新确认。通道只是加速协作，不能充当唯一恢复依据。
- 完成状态改变后直接触发相关待办。心跳和监控读内存计数；不设置每 30 秒重新加载历史的“保险刷新”。

主 CEX/期权 writer 与低频 collector 不共用该状态管理者。跨进程的盘口队列仍按原 Redis/spool 与 `ingest_batch` 协议交付，不能为省查询而移除 writer 的持久提交确认。

## 4. 提交与 checkpoint 的一致性

### 4.1 保留真实提交语义

当前 Across、Reserve、LST、Keeper 的低频写方法成功返回表示 MySQL 事务已经提交。它们没有经过 CEX 的 Redis 分钟异步 writer。本改造保留这个语义，直接用已验证的提交结果更新内存；不新增按批轮询 MySQL 的常态工作。

必须区分三个状态：

| 状态 | 含义 | 能否据此推进已完成游标 |
| --- | --- | --- |
| 已获取/已冻结 | 已有来源响应或稳定批次，尚未确认数据库提交 | 否 |
| 已持久交付/结果未知 | 有可恢复副本，但数据库可能未提交，或调用结果不确定 | 否 |
| 已提交并完成领域核验 | MySQL 成功提交；所需成员、分页、收据或最终性条件也满足 | 仅推进该条件对应的连续进度 |

不把 `ingest_batch` 强行引入每条低频记录。低频沿用各自 capture/batch、revision、成员摘要和提交语义；CEX/期权仍用已有方案规定的 `ingest_batch`。

### 4.2 跨 MySQL 与本地状态的恢复顺序

本地文件与 MySQL 无法作为同一个事务提交，因此明确保留两者之间的恢复依据：

1. 冻结稳定操作身份、批次内容、首次来源/可用时间、摘要及计划修订。保存现有 pending payload；没有现成 pending 的路径增加定类型冻结文件。不能每次重试生成新 ID 或改写观测时间。
2. 在允许数据库写入前，持久记录操作意图：操作身份、payload 引用及摘要、领域范围、预期旧/新修订、producer、后续状态变化所需信息。已有 Keeper `Ops` 或 LST pending 能提供相同证明时复用，不重复保存 payload。
3. 调用原领域写入方法，保留代次锁、幂等和完整性检查。超时/断线按“结果未知”保留同一操作。
4. 明确成功后，向管理者提交结果，增量更新内存。失败或不确定结果不会推进完成进度。
5. 将新的进度、完整待办变化及已应用操作边界一起写入 checkpoint。新产生的子待办必须在同一次持久状态更新中可恢复，不能先删除父操作后再记录子任务。
6. checkpoint 文件及目录同步成功后，才能清理它已经覆盖的恢复记录和不再需要的 pending 引用。仍未完成的操作继续保留。

checkpoint 可以合并写入。第 2 步持久化屏障不能因合并而省略；第 4 步后不必每个操作再独立 fsync 一整份状态，因为第 2 步的意图仍在，崩溃后可按身份核验。操作不能在 checkpoint 覆盖之前被 ACK、裁剪或由后台清理掉最后一个恢复副本。

对于不经过数据库的关键状态，例如来源预算扣减、分页 token 和即将发送的不可重复请求，沿用现有先持久化再执行的要求，不能套用“等 MySQL 成功后再保存”。普通可重建的统计指标不需要持久化。

### 4.3 崩溃处理

| 崩溃位置 | 恢复行为 |
| --- | --- |
| 意图未持久化，未允许数据库写入 | 从原进度重新调度；不宣称新数据完成 |
| 意图持久化，事务未提交 | 用原 ID、摘要和冻结 payload 重试 |
| 事务已提交，返回丢失或内存未更新 | 按该操作的准确身份查询并验证提交/修订；应用结果一次 |
| 内存已更新，checkpoint 尚未完成 | 从旧 checkpoint 及保留的操作重做状态转移；不重复产生逻辑事实 |
| checkpoint 已替换，旧恢复记录未清理 | 按 checkpoint 已覆盖边界过滤旧记录，并核验摘要 |
| 内容或修订冲突、文件损坏、引用缺失 | 保留原件并停止受影响范围的推进，进入显式恢复；不得重新置空状态继续 |

对“查不到提交”的结果未知操作，不得直接推断服务端写事务已结束。完整复用已有方案的事务身份核对、回滚确认和同身份幂等重试规则。

### 4.4 控制状态自身的写入量

初始参数是隔离测试起点，实施时按真实对象大小调整：

- 无状态变化不写 checkpoint；有变化时可合并，初始每 30 秒或累计 128 个已完成且未纳入 checkpoint 的操作触发一次。达到数量门槛先完成 checkpoint，防止正常恢复尾部无限增长。
- 待确认操作使用带长度、版本和校验和的记录/现有 pending，不写完整历史副本。新的恢复记录分段，初始单段上限 4 MiB；checkpoint 成功后压缩已覆盖段。大量仍未完成的任务不是可丢弃日志，保留其身份和恢复引用。
- checkpoint 使用同目录临时文件、文件同步、原子替换和目录同步。保留上一份有效 checkpoint 及足以从它恢复的尾部；只有更新的 checkpoint 已验证且替代恢复链完整，才回收旧文件。
- 恢复记录解析只可忽略未越过持久化屏障、因此不可能已执行 SQL 的不完整尾写；中间校验错误或无法证明安全的尾写进入恢复错误，不静默跳过。
- 内存先按每个低频服务 16 MiB 的新增热状态预算评估，另计已有候选、业务对象及 pending payload。长时间积压时按任务身份分段持久化，仅装载调度所需部分；超限时明确限流和报警，不删除待办或改为全历史扫描。
- Keeper 保留已实现的冷候选分离和不变状态不重写；LST 复用原 pending 文件。不得为了统一接口给已有路径多加一份全量副本。

实现必须报告 checkpoint 字节/秒、fsync 次数、恢复文件峰值和内存。只有减少数据库读取而把同等压力转移成本地全量状态重写，不能算通过。

## 5. 按领域改造

### 5.1 Across

将 `captures` 的历史列表用途拆成：连续 raw/decoded 覆盖区间、未确认 capture 集合、raw gaps、partial repairs、收据/transfer 待办，以及仍需 probe 的订单。已结束历史留在数据库。

新 logs 批次提交后，直接从手中的 Deposits、Fills、Refunds 派生后续工作；receipt、transfer、revision 提交后按身份更新对应任务。保持收据任务的 `(chain_id, block_hash, tx_hash)` 身份、USDC 筛选、fee unknown 与完整收据区别、原重试策略及 live/catchup 区分。终结费用仍未知的尝试可以结束本轮调度，但其未知状态不能被改为完整。

删除正常运行中的三类全量刷新：`Watch` 的 30 秒 capture 加载、`maintenanceLoop` 每轮加载、`RefreshRepairReceipts` 定时重读全部相关批次。`PrepareRepair`/历史读取逻辑仅作为首次转换或显式重建工具，在正常重启已有有效状态时不执行全量恢复。

链节点查询仍检查需要确认的尾部和 finalized 锚点。发生重组时依据受影响的 block hash 使对应捕获、收据依赖和覆盖失效，再补采真实缺口；不能只把一个最大高度减一。保留现有 finalized hash 冲突为严重错误的规则。

### 5.2 Reserve

保存当前与 related manifests 的独立身份和覆盖依据；不能为了压缩把配置身份混成同一范围。

维护 canonical 未确认集合、必要 finalized 哨兵、连续日志覆盖、最新有效 attempt 及其未完整收据任务。从新批次和修订的提交结果更新，`Reconcile` 只处理工作集合，`RepairReceipts` 只选择到期任务。

保留现有最新 attempt 的选择规则以及 `LogCoverage`、`ReceiptCoverage`、`Committed` 等条件。部分批次的 raw 覆盖不等于收据完整；不同进度不能被一个“成功”布尔值替代。修订不会重新采集旧时点报价，也不改写原 available 时间。

### 5.3 LST

保留原 `pending-batch.gob`、日志游标起点、manifest 校验、来源配额及整数/十进制路径。改造 `FlushPending` 的清理边界：数据库已提交的 payload 若仍是状态恢复的唯一依据，须等新的状态 checkpoint 覆盖后再删除，或先持久保存足够的状态转移记录。

增量维护待最终确认的 market、未完成 followup、按原时间窗口与排序规则选择的 gas 候选。新 logs/market/gas/followup 批次提交后更新，不再每次 `GasPass`/`finalizePending` 重读历史。GasPass 的十笔预算及候选确定规则保持不变，不能以缓存淘汰改变样本集合。

已有代码在启动时重算连续前缀，是为防止“本地游标在、数据库事实不在”。替代它的前提是本方案的持久提交证明、完整恢复链和数据库还原失效协议全部通过测试；不能仅删除这段校验来获得快速启动。

### 5.4 Keeper：在已有修复之上实施

先保留并完成已有文档第一步：服务端查询期限、上下文期限、单任务在途、退避及按窗口分页。这些接口也继续用于受控恢复和必要的提交核验。

之后扩展现有 `State`，为尚未完成的来源窗口保存 scan 身份、页链关系、分页结束证明、父 capture 身份、已提交 enrichment 子任务和完成条件。必须按原 `indexWindowComplete` 规则核验同一窗口的完整分页链，而非仅统计页数或拿最后 token 为空作完成依据。

父批次和 enrichment 提交后触发本窗口状态更新；只有索引窗口和必要子任务都完成，才能推进连续 `EvidenceCursors`。`EventCursors` 继续表示另一层进度。空闲轮询不反复调用 `KeeperEvidenceFrontier` 来重算已知状态；现存历史窗口只在一次转换/恢复时装载未完成部分。

Keeper 需要改动 `collection.go`、`collector.go`、state/checkpoint 的交叠部分，在已有 Agent 的修复合入后顺序实施，不同时重写同一接口。不得恢复旧的宽行排序查询或撤销已加的执行期限。

### 5.5 主 collector 与其他路径

本轮不改盘口编码、Redis 分钟交付、writer 并发或不可变元数据缓存。对主 DEX、资金费等做同类调用清单审计：区分启动恢复、工作集合读取、外部数据查询及历史报告。只有确认存在正常循环全历史重建的路径才迁入本机制；不因为接口里有 SELECT 就删除它，也不声称尚未测量的分支已是主要负荷来源。

## 6. 首次转换、正常重启与外部写入

### 首次转换

1. 对目标服务停止分派新任务，等待在途操作完成或登记为结果未知，持久保留 pending。记录实际采集暂停区间；不能补回的实时观测仍明确标缺失。
2. 目标范围禁止其他 collector、历史导入、人工修复同时修改。获取专用进程/转换锁，并核对现有 producer generation；不以文件锁替代数据库代次保护。
3. 从冻结的已提交数据和现有 pending 构建初始状态。按键分页、窄字段读取，需要明细才按准确批次读取。范围按领域确定：所有未完成和未确认项必须完整，followup 等保留原窗口，连续覆盖不能用任意“最近 N 条”代替。
4. 这次重建可能仍需读取全部适用的历史登记，明确作为一次转换成本；使用独立受限恢复入口，可断点续做，不放进每次 systemd 重启的默认流程。不能用 `LIMIT 500` 只取第一页后声称已全部恢复。
   输入清单必须标明已迁入、待迁入和不可读范围；没有迁入的记录不能被解释成“没有待办”。已存在的完整恢复依赖按原切换协议保留，无法证明依赖齐备的范围维持未知/待恢复，不能因为完成状态转换就宣称历史完整。
5. 用旧逻辑在同一冻结输入上对照游标、所有待办身份/状态、分支、最终性及边界证据；生成可核验的转换清单，保存原状态备份和新版 checkpoint。
6. 验证后启动新实现，以内存状态驱动运行。转换失败不发布半份 checkpoint，也不重置起点从当前链头继续。

首次转换使用新格式的操作不强行套用旧 pending 的数据形状；提供显式版本和转换器。现有 payload/源历史保留，不删除旧事实。

### 正常重启

正常启动检查数据库目标、服务、manifest/config、schema/状态版本、producer 代次、checkpoint 校验和及恢复引用；加载持久状态，恢复尚未覆盖操作，按准确身份核验提交和必要链边界。不自动遍历完整历史。

状态不能仅靠“最新时间戳”补增量：历史导入会插入旧时刻记录，修订会改变旧 capture。恢复依据是明确操作身份和完整性条件；不是 `WHERE time > last_time`。

数据库备份还原、数据目录替换、切换目标库、人工删除或修改业务记录，会使原状态可信性失效。部署/恢复工具必须记录新的数据恢复世代并作废受影响 checkpoint，经过显式重建才能恢复推进；仅比较服务器 UUID、最大区块或原 producer generation 不能证明数据库没有回退。未知来源的库变化不得靠一次尾行查询就宣称全历史一致。原有历史 verified/缺口状态也不因 checkpoint 存在而改变。

### 历史迁移与人工修复

常驻状态默认由一个 collector 管理。历史导入不能在它不知道的情况下补入会改变当前待办/覆盖的记录，然后期待定时扫表自动发现。

- 不影响活跃状态、已最终确认且无需后续工作的纯历史，按现有迁移协议导入，不触发状态刷新。
- 涉及未完成窗口、旧缺口、canonical/finality 修订或待跟踪对象时，导入前按冻结清单识别范围；不确定时按有影响处理。
- 首版采用明确的维护交接：暂停受影响服务的工作，提交并核验有限导入/修复范围，按明确 ID/范围更新状态并持久保存，再恢复。该范围可能小于全部历史，但不能用时间戳替代清单。
- 若未来需要同范围在线多写者，再单独设计持久变更通知；本轮不增加 CDC、轮询全历史或另一套永久事件日志。

历史迁移仍遵守已有方案的容量门槛和 30/60 秒降速、停接新块规则。状态改造未完成验收前，不据此提前恢复全历史导入。

## 7. 与写入积压方案的逐项衔接

核对版本：`write-backlog-improvement.md`，SHA-256 `89640de1249a25b14ce4cfd0d8f02128abb3ef3dc6bd6adda3e1162e9fadeff4`。后续若该文档修改，应重新检查下面的交集，不能把当前结论当作对未来任意版本的保证。

| 已有方案 | 本方案的处理 | 一致性约束 |
| --- | --- | --- |
| 第一步 Keeper 慢查询止损、限时、分页、索引 | 先实施；新状态机制进一步减少正常查询调用，恢复路径继续使用修复接口 | 不撤销执行期限和完整分页验证，不另设更大的常驻读池 |
| 第二步 Redis/spool 调度、租约、单 writer 进程锁 | 原样保留 | 新状态锁只保护对应低频服务，不占 writer 的锁；不改 `.batch` 格式、队列 ACK 或批次唯一身份 |
| 第三步连接池、不可变元数据缓存、批量写入 | 原样保留 | 本方案的可变运行状态由单一管理者维护，不能放进“不可变元数据缓存”；不共用可变 `SetProducer` |
| 第四步 CEX/期权分钟共享代次锁及 `ingest_batch` 占位 | 原样保留 | 低频及修订仍用原独占事务；不全局替换 `FOR UPDATE`，不重复新增批次提交表 |
| 实时账户总连接配额与有限 worker | 复用现有池 | 状态管理者不占新长连接；恢复与实时分阶段、按已有总配额运行 |
| 持久化、`noeviction`、未提交数据保留 | 原样保留 | 状态文件不证明数据库完成；未完成任务不套用 Redis 分钟 TTL。2026-10-16 用户明确要求关闭 binlog，此项以最新指令为准；fsync/redo/doublewrite 保持 |
| 先修 Keeper，再切 writer，最后容量验收 | 保留为当前止损主线 | 本方案的 Across/Reserve 优化是补充；Keeper 状态重构在已有修复之后合入，writer 上线不依赖全部状态改造完成 |
| 不新增通用任务事实表 | 遵守 | 新增的是可压缩、可恢复的本地运行状态；不把每次状态变化永久写入另一张通用历史表 |
| 60 分钟回放、24 小时持续观察、实时稳定后迁移 | 原样保留并增加状态验证 | 新方案的少读指标不能代替已有吞吐、积压和完整回放指标 |

第一轮提交尽量限于领域 runner/state、新的本地持久化辅助及测试。共用 `mysql/client.go`、`producer.go`、writer、Redis/spool 的改动继续由原方案负责；本轮只有确有必要的按身份恢复读取接口才修改 MySQL 领域文件，并在原修复合入后实施。

## 9. 测试与验收

### 正确性

1. 冻结相同事实和 pending 输入，以旧恢复逻辑作对照，比较全部游标、缺口、待办身份、状态和后续选取顺序；包括空集、老未完成任务和 related manifests。
2. 在意图落盘前后、COMMIT 前后、结果通知前后、checkpoint 替换前后及旧记录清理时注入崩溃；恢复后无提前推进、无丢任务、无新身份重写旧事实。
3. 重复、乱序、旧 revision 和内容冲突；通知通道满、worker 失败、checkpoint 写失败/磁盘满，均不产生假完成。
4. 链重组、同高度不同 hash、finalized 冲突、多段缺口、partial receipts、raw 与 decoded 覆盖不同；不能以最大高度跨过缺口。
5. Keeper 同一窗口跨过数据库每页 256 条记录的边界、来源重复页/缺页/空页、父子批次未完成及长时间退避，保留原严格分页链判断。
6. LST followup 到期、31 天边界、gas 候选排序与采样、pending 已入库但未更新游标，结果与原规则一致。
7. 首次转换中断、旧格式转换失败、checkpoint 损坏或丢失、数据库还原、人工修复和历史导入，均能识别失效并走受控恢复。
8. 使用 race 检测验证状态管理者及 Across 网络 worker 的对象隔离；单任务最多一个在途请求。
9. 联合版本完成 AGENTS 与已有写入方案的全部必需验证：新 5/10 档、旧 10/50 档及混合历史精确回放，同秒最终值、零数量删除、无变化与无效秒、序列断档、来源严格解析和定点数精度等。原完整性门槛不因本次主要改状态而取消。

### 读取与资源

以同一输入速率、相同有效待办和相同持久化配置，分别测试历史量为 H 和 10H、但活跃工作相同的隔离数据集。采集种类、批次大小、是否编译、是否历史导入及其他服务负荷全部记录，避免不同负载之间直接比较。

- 各已改造正常循环的“全历史状态重建”调用数为 **0**；无新结果、无到期待办时，不为询问自身进度而访问历史 capture 表。
- 历史量增长时，稳态状态检查的逻辑读取量和热状态内存不随已结束历史近似线性增长。初始性能目标为 H 与 10H 的中位稳态耗时差不超过 20%；同时报告绝对耗时、扫描行数和噪声，不能只凭比例通过。
- 正常重启只处理 checkpoint、未覆盖操作及必要边界，不扫描全部历史；分别报告正常重启和首次/损坏重建成本。大量真实未完成任务的恢复成本单独披露。
- 记录 MySQL 文件/容器物理读写、SQL 扫描与返回行数、延迟、checkpoint 写入与同步、RSS、swap。进程与其已回收子进程的 I/O 计数不得相加重复归因。
- 每 10 秒输出内存汇总：当前连续进度、缺口数、待确认/待补数、在途数、最老待办、checkpoint 年龄与大小、未覆盖操作数、错误状态。不要为计算这些指标再次扫历史。
- 最终性能验收复用已有方案的至少 60 分钟完整负载回放、至少 `1.5 × R` 积压处理能力及 24 小时持续运行要求；磁盘忙碌比例和吞吐均记录，不仅看 Windows 是否低于 100%。

## 10. 部署和回滚

部署前保存每个服务的旧二进制、配置、状态文件及恢复引用，记录实际源码状态和新二进制哈希。使用真实 user systemd 服务及已有路径，不用可选 Compose 代替现场部署。

每次只转换一个服务，在途事务结束或明确登记未知状态后切换；按上一节核验后再推进下一项。文件锁和 producer 代次遵守原协议；不得通过改写旧 pending 的 generation 解决升级问题。

状态格式上线前必须具备版本检查和恢复/导出工具。回滚时先停止新任务并处理在途，依据新版 checkpoint、保留的未决操作及已经提交的事实，生成旧版可用的状态；若旧版本来从数据库重建，安排一次受控重建，计入恢复成本。不能直接换回升级前的状态备份，丢掉升级后新产生的待办。

未决操作按原身份核验/完成后才交给不认识它们的旧程序。无法无损转换时停留在可恢复状态并处理受影响范围，不启动旧程序猜测进度。回滚保留所有已接纳数据和已提交事实；现有 writer 方案的队列、提交、索引回滚规则继续适用。
