# doublewrite 写入放大原因及解决方案

本轮回答“主业务约 3 MiB/s，保护文件约 6 MiB/s”的原因，并给出实施方案。**已经确认主因是 8 KiB 压缩页与 16 KiB doublewrite 槽位的尺寸差异。**生产配置、DDL 和官方对应版本源码相互吻合。本轮没有修改生产参数、表结构、服务或数据。

## 已确认的机制

生产只读回读：MySQL **8.4.11**，`innodb_page_size=16384`，`innodb_doublewrite=ON`，`innodb_doublewrite_pages=128`。两张质量热点表及 `source_batch_status` 的实际 `SHOW CREATE TABLE` 均为 `ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8`。

MySQL 8.4.11 源码路径：

- [`Double_write::prepare`](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/buf/buf0dblwr.cc#L1305) 取压缩页内容和该页的物理尺寸。
- [`dblwr::Buffer`](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/include/buf0dblwr.h#L65) 采用实例全局物理页大小作为槽位步长；复制压缩页后，指针仍前进一个完整槽位。
- [`Batch_segment::write`](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/storage/innobase/buf/buf0dblwr.cc#L1359) 写出整个已使用槽位区间。

因此对于一个 8 KiB 压缩页，一次常规刷页对应约 **8 KiB 数据文件 + 16 KiB doublewrite 文件 = 24 KiB**，还没有计入 redo 等其他写入。保护槽位中的有效内容仍可以是压缩页，不能误说成 MySQL 将副本解压后保存。这里的“3 MiB/s”也是业务文件刷页量，不是每秒新采集记录的净大小。

17:09–17:11 原始样本进一步支持该机制：

| 项目 | 两分钟增量 |
| --- | ---: |
| doublewrite 文件写入 | 794,574,848 字节 |
| 对应 16 KiB 槽位数 | **48,497，整除无余数** |
| 所有数据/undo 文件写操作数 | 48,532 |
| 所有数据/undo 文件写入 | 448,569,344 字节 |
| 数据文件平均每次写入 | 约 9.03 KiB |

主库业务文件约 3.27 MiB/s；将其他业务库、undo 等数据文件计入，约 **3.55 MiB/s**，doublewrite 为 **6.29 MiB/s**。两种文件的采样不是原子操作，写请求也不必总等同一页，所以两者相差 35 次不能作为异常证据；16 KiB 槽位机制已有源码确认。

证据：`var/storage/io-attribution/20261019T090934Z/doublewrite-accounting.json`；现场参数和 DDL：`var/storage/io-attribution/doublewrite-20261019T095803Z/`。后者的十秒状态/文件采样存在先后顺序，只用于补充核验，不能与前一轮两分钟混算。第一次查询 `INNODB_TABLESPACES` 超时，随后改用三张表的有界 `SHOW CREATE TABLE` 成功核验；没有扫描事实数据。官方源码下载至临时目录供阅读，没有编译或执行。

## 方案一：保留完整保护，减少需要刷出的页，建议优先实施

doublewrite 的当前实现没有把本实例的单个 16 KiB 槽位单独改为 8 KiB 的调参项。实际可行的应用侧方法是减少页数和同一页的重复刷新，这会同时降低业务文件与保护文件的写入。

实施分两项，并分别测收益：

1. **目录质量证据改为共享 profile 与分钟成员引用。** 已有真实数据原型显示：约 2,950 个成员仅对应 7–11 组目录证据字段。相同字段保存一份，成员保存引用；保留定类型字段、原内容哈希、来源身份、时间和有效性。[既有设计及原型](io-reduction-20261016.md)已列出读写与回退要求。原型的 94% 是部分逻辑字段缩减，不能当成数据库总写入降幅。盘口质量整组共享此前反而增大逻辑字节，不纳入这一改造。
2. **对质量表试验按分钟集中写入的物理布局。** 当前盘口质量主键为 `(instrument_id, minute_time, compact_batch_id)`，目录证据为 `(run_id, instrument_id, minute_time, compact_batch_id)`；每分钟为大量 instrument 追加数据，会访问分散的页尾。候选结构将分钟提前，让同一分钟的宽记录较集中写入；同时保留支持 `(instrument_id, minute_time)` 等原查询的窄索引。新索引有额外成本，必须计入总量，不能仅凭主表变小上线。原哈希、批次冲突和重复历史语义全部保留。

先在隔离库比较“原结构”“只调整布局”“布局加目录共享”三组相同输入，使用覆盖活跃/非活跃流及完整规则刷新周期的至少 60 分钟数据。计量业务文件、redo、doublewrite 总字节/成员；控制初始缓存状态，并在比较结束时偿还脏页差额，避免把延迟刷盘当作节省。同时验证批次提交 P95/P99、8 KiB 慢读次数及所有秒的精确回放；共享引用与成员必须同事务提交，重试不得掩盖冲突。

验证通过后只切换新分钟的写入，查询兼容旧表，不为启用新格式全量重写历史。回退关闭新写入开关，但继续保留新格式读取能力。该方案是减少写入源头，不承诺固定节省比例；验收要求总写入有可重复下降且提交/查询不退化。

## 方案二：快速减少保护写入，接受恢复能力下降

MySQL 支持 `DETECT_ONLY`：只保存用于检测不完整页写的元数据，不再保留可用于修复的整页副本。它可从当前 `ON` 动态切换，通常无需重启；这是可靠性取舍，不是等价优化。[官方模式定义](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)

若明确接受该取舍，拟执行的命令为：

```sql
SET GLOBAL innodb_doublewrite = 'DETECT_ONLY';
```

需要恢复完整保护时：

```sql
SET GLOBAL innodb_doublewrite = 'ON';
```

预期可移除原 6.29 MiB/s 中的大部分整页保护写入，只留下较小检测记录；实际收益须以同输入测量，不能承诺整盘忙碌率同比下降。该模式仍有写入，不等同于 `OFF`。

代价是异常断电、存储故障或进程退出造成不完整页写时，可检测出问题，却不能从 doublewrite 自动恢复完整页。redo 不能作为同等保障；已经从 Redis 短期队列回收的历史也不能假定可以重采还原。必须事先有可验证的备份/恢复路径，且明确接受备份之后可能丢失的数据。切回 `ON` 只恢复后续保护，不能追溯修复此前受损的页。

当前“给出解决方案”没有授权降低恢复保护，本轮不执行该切换，不写持久配置。若选择该方案，先核验恢复方案，再做有限对照；不能因回读成功就宣称没有完整性风险。

## 不优先采用的做法

- **降低 `innodb_doublewrite_pages`**：改变批次容量，不改变每页 16 KiB 槽位，不能直接解决 8/16 KiB 比例，还可能增加写入/同步次数。
- **关闭表压缩以使两边字节相等**：可能只是让业务文件从 8 KiB 变为 16 KiB；相同页数下总量由 24 KiB 变为 32 KiB，比例好看但写得更多。实际页数也会变化，必须实测。
- **改全局页尺寸或自编译数据库以压紧 doublewrite**：涉及实例/恢复格式及整体页布局，不属于可直接上线的小参数修改，不根据单页尺寸推导固定收益。
- **将 doublewrite 放到同一块盘的另一个目录**：不会减少该盘写入。真正独立存储可以分担设备负荷，但总写入仍在，属于扩容分流而非减少磁盘消耗。
- **直接关闭 doublewrite、依赖 SSD 或 UPS 宣称安全**：不能据设备类型证明整条虚拟化/文件系统/存储链路的数据库页原子写入能力。

建议先实施方案一；如果当前首要目标是立即大幅削减保护写入，方案二是明确、可操作的选择，但必须同时接受其恢复能力下降。两者都不能单独解释或保证消除上一轮测得的高延迟小块读取。
