# 切换与历史迁移

## 顺序与边界

采用“新采集先上线、旧历史后迁移”。迁移期间不提供完整历史报告，也不实现跨 ClickHouse/MySQL 的在线历史拼接查询。新端仍需执行内部健康检查、数据库恢复读取与新分钟回放。

切换以服务和数据库为单位，允许逐个完成。每个服务保存独立切换记录：旧二进制/配置摘要、旧端最后完整批次、停止时间、未完成批次、恢复游标、MySQL 生产代次、新进程启动时间、新端首个实际有效批次及缺口。展示可用北京时间，存储记录使用 UTC。

不要将一个全局时间 T 当成所有表的唯一分割条件：新服务可能补写 T 之前的实际资金费，链上历史批次可能在 T 之后得到最终性修订。新旧冲突必须按业务身份与原版本语义判断。

## 切换前准备

1. 刷新数据库 allowlist、表清单、列类型、ALIAS、排序键、引擎与修订列。与本目录快照比较，新增或改变的模型先补映射；不自动扩大到其他项目。
2. 安装独立 MySQL/Redis 和 writer；完成隔离集成、故障恢复和吞吐测试。准备每张表的正式 DDL、schema version、读写账户和空间预算。
3. 保存五个旧服务的程序、unit、非敏感配置摘要及已有 pending/state 文件清单。构建源目录有未提交内容时保存快照，不能只记 Git HEAD。
4. 预导入下述启动依赖，可在旧端继续采集时先搬大部分；停止相应旧服务后必须补齐尾部并重新验证。
5. 演练同一个服务只存在一个 writer。旧进程退出、状态目录锁释放之前，不启动新采集进程。

### 新采集启动所需的数据

实际复制范围以[新版启动调用复核](startup-dependencies.md)为准。原 59 表清单是保守整表预置清单，不是必须搬完的启动闭包；尤其主库发布历史、来源证据及全部 DEX 报价不能直接作为切换前提。

| 依赖 | 最小要求 |
| --- | --- |
| instrument 与收益路线身份 | 原库全部 ID 与完整身份；新号分配从已有最大值继续，并在数据库事务中防并发碰撞 |
| 规范化映射、规格与规则 | 当前使用 revision 的完整依赖；旧合约版本不改名、不重编号 |
| 期权 run/catalog/plan/lifecycle | 当前计划、成员、规格、规则及恢复所引用的证据；新 session 仍按原规则建立，不把旧活跃状态当成当前有效连接 |
| 发现事实 | 未完成 intent 的原内容与首次已知时间、来源证据、已发布状态；不能重置 known_from |
| 资金费率 | 当前实际值与待确认集合；避免已确认 actual 被新进程 estimate 覆盖 |
| DEX、Reserve、Across、LST、keeper | 恢复代码会读取的 capture、成员事实、共享收据、修订、日志覆盖、待确认/待补数据，以及其引用的 metadata |
| 本地运行状态 | 原 pending、日志游标、扫描起点、manifest、来源 gate、冷却及锁协议，逐项核验关联数据 |

源代码中 Across、Reserve、LST 会通过历史 capture 和成员验证恢复覆盖，不信任游标文件里的 Next。因此“拷一个游标文件就启动空库”不可行。bootstrap 必须列出由恢复代码实际需要的全部依赖并验证闭包；不能只迁移任意的“最近一分钟”。

对于四个独立低频库，优先在切换前预置该在用库的完整逻辑内容，规模远小于主库盘口历史，也最容易保持现有恢复语义。主库的 DEX/收益/发现事实依赖按实际恢复调用确定。这个准备工作是保证新采集可运行的初始化，不要求在切换前迁完整 CEX/期权历史。

若某个恢复闭包因为坏块或缺成员无法成立，保持该服务旧端运行并先处理该问题；其他已具备条件的服务可以继续切换。不能为了满足同时上线而让缺数据的新服务重置游标、从当前高度重新起步或静默放弃旧缺口。

## 正式切换操作

按五个服务逐项执行，具体顺序以依赖和隔离测试完成情况确定：

1. 暂停该服务的人工/定时回补入口，保留原来源限速和冷却记录。要求旧端在分钟边界附近优雅退出，等待完整批次 drain；保存未完成批次及最后提交边界。
2. 确认旧进程已退出、没有同库遗留 writer。不要为切换重启共享 ClickHouse，也不要修改其他项目数据库。
3. 完成 bootstrap 最后增量同步，执行该服务真实恢复读取，核对成员摘要、ID 分配起点、canonical/finality、待确认集合和游标。
4. 在 MySQL 建立新 producer generation，安装新程序，显式选择 MySQL/Redis 后端，再启动新服务。配置缺失时应报错，不能悄悄写回 ClickHouse。
5. 核验实际数据：CEX 新分钟及有效位持续推进；期权按真实计划核齐分片；低频按原调度和来源可用性提交。监测 Redis 队列、持久化和 MySQL commit，不以 unit active 代替数据验收。
6. 主 collector 至少观察连续 10 个分钟周期并逐批核对覆盖；序列断档或来源故障造成的无效秒必须有对应诊断，不能为凑全秒而改数据。低频按来源周期核验，启动未到计划时间的来源标注等待，不强行频繁调用公开 API。
7. 将旧端源库标为本项目采集已停止写入，记录实际冻结清单。保留查询权限和源数据；在新端健康后开始该库的完整历史迁移。

没有第 0 秒有效起点的 CEX 过渡分钟不伪造完整分钟；以现有模型允许的缺失/质量记录表现。链上漏扫可按原规则回补，实时盘口和错过的实时 Quoter 报价不能回补为当时观测。

## 源冻结与迁移单元

每个旧库在对应 writer 全部停止、最后提交已核对后固定逻辑源范围。清单包含 database/table、DDL 摘要、引擎、物理与逻辑键、分区、源时间/键范围、导出编码版本及状态。后台正常 merge 可以继续，但不得运行会改变业务结果的写入、mutation 或清理。迁移器监测源结构与写入变化，发生变化时停止相应范围并重新冻结，不能沿用旧完成标记。

源 physical part 名会因 merge 改变，因此断点以冻结的逻辑键范围和摘要为准，不能只记“最后导出的 part”。源有同键不同值且无明确版本时，先确认原 FINAL 选择是否稳定；有歧义的范围记录为冲突，不能随意取一条。

表读取策略：

- ReplacingMergeTree：在有界分区/键范围内按源逻辑去重规则读取，使用 FINAL 或已经证明等价的版本读取；canonical/committed/finality 筛选在正确解析版本之后进行。
- 普通 MergeTree：不用 FINAL，不执行 DISTINCT。保留所有行、物理重复次数和原有发布歧义，避免使原本非法的事实变成合法。
- ALIAS：从冻结的物理列读取，通过已验证的 compact 解码恢复业务值。不可把源 ALIAS 和它对应的紧凑物理列都当独立事实，导致行摘要或成员数翻倍。
- 不完整或未发布事实：迁移其原状态用于诊断，不自动为它们制造提交行。

“保留全部历史”指保留项目查询语义所承认的逻辑历史、原有无效/缺失状态和必要证据。ReplacingMergeTree 已淘汰或将淘汰的重复版本不等于可用业务历史；本轮仍保留 ClickHouse 源文件，不能用逻辑迁移完成作为自动删除源库的依据。

热表按 UTC 月定位，再按分钟/日期和排序键分块；每块开始可设 1–5 万行及 16 MiB 未压缩上限，超限继续细分。源查询设置执行时限和内存预算；不能对几亿行表使用无界 OFFSET 或一次全表读入内存。大表迁移顺序优先近期完整批次，然后向较早日期推进；独立历史/验收库最后搬迁。

每个分块经过 `planned → copied → verified`，失败另记状态和原因。逻辑块 ID 由 migration run、源库/表、键范围、DDL/映射版本生成，不依赖临时文件路径。

## 导入协议与冲突规则

迁移器每次处理一块：

1. 从冻结源读取显式物理列，解码并完成类型/长度检查；计算规范化内容摘要、逻辑键范围、行数及必要重数。
2. 使用该表的目标映射写入 staging 或最终事实表，SQL 批次有行数和字节上限。提交控制行与实际事务对应；不在持久化前推进断点。
3. 重读 MySQL 目标块，解码到相同业务值，计算可比较的计数与摘要。当前新写入会更新的表，按照下表核对“源值或有证据的更高版本”，不能仅按总行数判等。
4. 跨表批次的全部成员齐全后，验证原领域摘要、引用和质量规则，再恢复原提交可见性。历史 commit 不能领先于所需成员导入。
5. 原子保存 verified 状态。重跑 copied 但未 verified 的块必须先重读核验，不能直接跳过。

| 表或冲突类型 | 目标规则 |
| --- | --- |
| instrument、contract spec 等身份 | 同 ID 全身份必须一致；导入时不重新分配。冲突阻断相关依赖 |
| 不可变盘口批次/成员/计划 | 同逻辑键同内容幂等；不同内容进入 conflict，禁止覆盖新数据 |
| revision 型 capture、dex_block | 原 revision 大者生效；同 revision 不同内容为错误，不按迁移时间裁决 |
| dex_tx_receipt | 按原 available_at 版本及共享收据校验处理，不能把较旧收据覆盖新修订 |
| funding_rate_hourly | actual 优先于 estimate；同优先级不同内容需原规则或明确来源版本证明，不能直接 INSERT IGNORE |
| 无版本 ReplacingMergeTree | 源内先解析源逻辑版本；与新端同键不同时记录冲突，不能假定迁移晚到就更新，也不能一律无声丢弃源值 |
| 普通 MergeTree 发布表 | 保存源行重数；重复发布在 MySQL 查询端仍返回歧义/不完整，不降为一个合法发布 |

对普通 MergeTree 表，正式映射增加内部 `occurrence` 列，物理主键为完整业务键加 occurrence。新的唯一发布使用 occurrence=0；源键有多行时稳定排序全字段规范字节，逐行编号保存，完全相同的重复也保留多次。迁移映射保存源重数；读者按业务键检查数量，不能用 `LIMIT 1` 掩盖重复。新 writer 遇到历史歧义键必须拒绝复用。源同键组不跨迁移块拆散，块过大时使用有界磁盘临时数据。

目标已有 live occurrence=0 时先对照源组：相同的单行可直接幂等核验；源组本身重复或内容冲突时，先在该表的定类型 staging 保留完整源组并登记阻断状态，按源重数和目标来源记录明确合并，不能机械追加而把同一行算两次。未完成裁决的业务键禁止进入完整历史查询。

对“旧版本被新端更高版本取代”的记录，保存源摘要、目标摘要、双方版本和裁决理由。验证结果应是源内容被精确保留或按原业务规则被新版本覆盖，不能要求所有可变目标字段永远等于旧库快照。

## 历史校验

全字段摘要统一以逻辑类型、NULL 标记、数组顺序和精确数值生成，不比较两种数据库导出的 JSON 文本，不经 float 解码；逐块使用有序记录序列或严格定义的多重集摘要，简单 XOR 不足以验证重复次数。

验证层次：

1. 所有清单表都有目标映射；空表同样有结构与结果记录。
2. 所有迁移块回读通过行数、重数、字段摘要和键范围校验；计数采用相同去重口径，不能与 `system.parts.rows` 直接判等。
3. 所有已提交领域批次核对成员数、成员哈希、计划、证据与共享引用；未提交及无效状态保持原样。
4. 对旧 50/10 档、新 5/10 档、无变化、删除、缺失和跨切换范围执行逐秒回放对照；全部导入盘口分钟进行结构/有效位/差量应用检查，代表性样本再与源端实际回放逐价比较。
5. DEX/Reserve/Across/LST/keeper 用原读取接口恢复批次与游标，确认没有把重组分支或未最终确认数据变成最终数据。
6. 对使用者开放报告前，核对每个查询范围均处于 verified；之后遗漏范围仍返回明确历史未就绪/缺失状态，而不是空结果伪装“没有市场数据”。

## 限速和进度

历史迁移初始一个 worker，实时连接池独立。每 10–30 秒记录导入行/字节数、剩余块、校验积压、冲突数、最老实时 pending、MySQL 提交耗时、磁盘余量与 I/O。先完成一批真实端到端迁移及校验，再根据验证吞吐估算剩余时间；不把此前小样本 INSERT 速度直接换算成全量 ETA。

采样或写入延迟升高时降低导入配额；达到实现文档中的保护阈值时停止新历史块，已经开启的有界事务结束后保持断点。迁移暂停不应停止新采集，也不应改变 Redis 未确认批次的保留规则。

## 回退

回退分两种情况：

- **新端尚未接受任何新事实**：停止新进程，确认状态目录未被不兼容修改，恢复旧程序和配置，再启动原服务。
- **新端已接受新事实**：先停止受影响新采集的接纳并保留/排空 pending；保存新端事实和状态。将新分配的身份、恢复所需的新批次及游标依赖同步回旧端，验证后才恢复旧采集。新端独有历史必须保留，不能靠把二进制换回去就宣布数据已经回退。

上线前至少实现并演练身份与恢复依赖的反向导出，或准备可运行的兼容旧业务版本但仍使用 MySQL 的回退程序。若两种回退路径均不具备，不应切换。禁止两个后端的采集器同时占用同一状态目录、来源身份或分配器。

新端失败期间无法采到的实时盘口如实记缺失。ClickHouse 是旧历史来源，不是 MySQL 切换后新写入的自动镜像；保留旧库并不自动等于拥有全部新数据的备份。

## 完成标准

最终交付应分别列出：

- 五个服务的切换和新数据健康结果，以及真实过渡缺口。
- 125 张基线表加执行时确认的变更清单，各表/块复制与校验结果。
- 未解决源坏块、历史缺口、同键冲突，若为零则给出对应检查结果。
- 新旧盘口回放和专项批次验证、24 小时资源指标、实际每日增长及容量预测。
- 历史查询开放状态、旧端保留位置、新端备份恢复方式及回退演练结果。

没有未解释差异且所有要求范围验证通过，才可宣布历史迁移完成。本设计不包含迁移后自动删除 ClickHouse 数据或停止共享 ClickHouse 实例。
