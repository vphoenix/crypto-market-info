## 优先候选：Redis 值的无损压缩

现状：spool 已压缩，但 `redisbuffer.acceptOptions` 仍把未压缩的 `optionPartType` 写进成员 `payload`；`WritePreview` 也把未压缩帧写进每秒 `s:xx`。这些都是已有定类型编码，没有 JSON。现有 AOF 会记录这些写入；持久化及重写机制见 [Redis 官方说明](https://redis.io/docs/latest/management/persistence/)。

本轮从真实 AOF 读取两个部分样本，另持有只读句柄等待自然轮转，完整解析一个 47,384,488 字节的增量文件。未复制/修改活动日志，也未触发重写。对该完整文件的 3,701 个候选值逐一执行 zlib level 1 压缩、解压和字节相等校验；小于 1 KiB 或压缩后不划算的值保持原样，试算为新信封预留 45 字节。

| 数据 | 原值合计 | 候选值合计 | 值字节减少 |
|---|---:|---:|---:|
| 期权交付 payload | 18.71 MiB | 2.11 MiB | 88.74% |
| 每秒预览 | 17.28 MiB | 8.20 MiB | 52.56% |
| 整份增量日志，其他命令保持 | 45.19 MiB | 约 19.50 MiB | 约 56.84% |

最后一行是替换值长度的离线试算，保留原命令开销，没有在 Redis 中回放新格式，也不是已验证的物理写入降幅。样本包含正常和无效质量状态，生产行情分布变化仍会影响压缩率。压缩 CPU 约 0.47 秒，属于 Python/C zlib 实验，不能替代 Go 热路径及采样截止测试。

Redis 约占本轮项目进程写入的 14.6%，且其写入包含日志重写；因此不能把 56.84% 套到整盘或项目总写入。合理结论是：这项候选有明确的重复字节可消除，值得做小规模实际 AOF 对照，总体空间有限。

落地要求：

- 只改变 Redis 值的物理信封，保留原定类型内容、交付身份及原文摘要；先部署新旧兼容读取器，再启用新写入。
- 解压前验证版本、长度和上限，解压后验证摘要；成员校验须针对原文，不能把压缩格式差异误判成内容冲突。混合格式重试、seal、WAITAOF、MySQL 提交证明和 ACK 顺序保持。
- 预览读取、清理时读取和交付读取都须兼容旧值；不减少秒级记录、不改变有效性、不关闭持久化。
- 同输入隔离回放比较 AOF 增量、基础文件、实际进程写入、解压内存、CPU 和采样超时；验收通过才做生产对照。先做期权 payload，再评估预览，避免一次引入两处格式改动后无法区分收益。

证据：`aof-probe-1.json`、`aof-probe-2.json`、`aof-full-probe.json` 及对应有界只读脚本。完整样本的文件大小输出最初被解析器同名临时变量覆盖；已修正脚本及报告字段，完整读到 EOF 的字节数和全部压缩统计不受影响。

## 次选：降低 Redis 日志重写频率

本轮约五分钟发生 5 次 AOF 重写、延迟 fsync 计数增加 1。当前基础文件约 42.63 MiB，设置为 `auto-aof-rewrite-percentage=100`、`auto-aof-rewrite-min-size=64 MiB`、`aof-use-rdb-preamble=yes`；`save` 为空，没有另行周期 RDB 快照任务。

这说明短生命周期数据在反复写增量日志之外，还频繁重写基础文件。若按当前基础文件大小粗算，5 次重写对应约 213 MiB/五分钟，约 0.70 MiB/s；这只是量级估计，不能把所有轮转文件都假定一样大，也不能在 Redis 进程计数上重复加总。

可对照把最小重写门槛提高到 256 MiB，保留 everysec、WAITAOF 和重写期间 fsync。代价是更多日志磁盘占用和更长重启回放时间；不是免费收益。本轮没有修改该值。应先评估值压缩后的重写频率，再决定是否还需要调门槛，两项潜在节省不能直接相加。

## MySQL：保留一个结构实验，其余暂不做

文件级观测：项目表空间写入约 2.485 MiB/s，doublewrite 约 4.555 MiB/s，redo 全局计数约 0.856 MiB/s，其他稳定文件约 0.197 MiB/s。redo 文件名会循环更换，按新文件名直接减基线会把历史计数当成本窗口，故报告排除这类文件并使用 `Innodb_os_log_written`；没有重置数据库统计。

项目表中，盘口质量约 0.772 MiB/s，目录证据约 0.391 MiB/s，盘口分钟和秒差量合计约 0.716 MiB/s。原目录证据共享原型仍值得做隔离物理对照，但 94% 的逻辑字段缩减不能变成 94% 的总写入节省；该证据表目前仅占项目表文件写入约 15.7%，其关联 doublewrite/redo 不能按表精确分摊。实现边界沿用[上一轮记录](io-reduction-20261016.md#后续结构实现的具体边界)，不直接重建历史表。

暂不建议：

- 继续降低 `io_capacity`：前一轮完整对照未证明稳定收益。
- 全表改主键或强行共享整组盘口质量：前者尚无同输入物理实验，后者已测出体积增加。主键决定聚簇存储且进入辅助索引，重新排列可能改善写入局部性，也可能增加查询成本，不能只看插入顺序。参见 [MySQL 索引说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。
- 再调表压缩页大小：当前已是 8 KiB 压缩页，窗口内压缩尝试 43,767 次、成功 43,385 次，失败比例约 0.87%；没有证据指向严重的压缩失败。页分裂指标未启用，零计数不代表没有分裂，本轮也没有为了猜测开启额外监控。
- 关闭 doublewrite、降低提交持久性或关 Redis AOF：会改变故障恢复保证，不作为本轮省盘方案。doublewrite 的恢复用途见 [MySQL 官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)。
- 缩减档位、减少采样秒数、删除质量字段或历史：会改变当前数据目标，不属于本轮无损优化。

除 Redis 压缩、压缩后再评估日志重写门槛，以及已有目录证据结构实验外，本轮没有找到值得立即继续推进的新方案。当前还存在期权质量缺口，优先级高于继续追求小幅写入改善。
