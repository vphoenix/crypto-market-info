# 新采集写入积压改进方案

2026-10-14。供后续编程、测试和部署使用。

目标是让新数据及时入库，同时消化已经落到磁盘的待写数据。执行顺序为：**停止慢查询反复叠加 → 修复队列调度 → 减少每批数据库操作 → 缩短事务并安全并发 → 排空积压并验收。** 保留当前 Redis、MySQL、数据编码和采集范围；不通过减少采样、放弃历史或降低持久化保证提速。

本方案给出实施与验收要求。2026-10-14 已开始部署，实际阶段状态见[实施记录](../../research/2026-10-14-write-backlog-improvement/report.md)；部署不代表全部验收通过。现有迁移的业务模型和恢复协议仍以[存储设计](storage-design.md)、[实施要求](implementation.md)及[切换流程](cutover-and-migration.md)为准。

## 问题和目标

10 月 14 日 17:02—17:07 北京时间的[现场检查](../../research/2026-10-14-writer-backlog/analysis.json)确认：

| 现象 | 对应问题 |
| --- | --- |
| 17:02—17:07 每个逻辑分钟至少有 88 个不同待写批次 | 当前输入规模已有明确下限；不是最终全量采集的容量上限 |
| 16:56—17:01 部分分钟仅提交 0—2 个期权批次 | 消费速度明显落后，需要减少每批耗时 |
| 17:07 有 6,821 个磁盘待写文件，约 2.4 GB；Redis 待写 195 批 | 两个存储可能保存同一批，不能直接相加当作唯一积压量 |
| 约 5 分钟增加 378 个磁盘文件和 58 个 Redis 待写项 | 积压持续增长；队列局部变小不代表整体改善 |
| 最老磁盘批次来自 15:32，抽查最老 12 批均无 MySQL 提交记录 | 存在真正的旧数据积压，需要保证处理机会 |
| 一次抓到 8 条 Keeper 长查询，最长 760 秒；结束检查时重启计数 24 | 客户端超时和重启未能保证数据库里的旧查询及时结束 |
| 多个主采集事务等待 `producer_generation` 的同一行 | 当前事务锁把本可独立的工作串行化 |

长查询数量会变化，后续快照中曾没有正在执行的 Keeper 查询；实施时重新核实，不能按旧连接 ID 终止进程。当前诊断没有得到可靠的逐函数耗时占比，以下优化按已确认的行为安排，不承诺某一项单独带来固定倍数提速。

设完整采集的实测输入为每分钟 `R` 批。正常入库能力必须大于 `R`；清理积压时，以 **至少 `1.5 × R` 的持续处理能力**作为初始容量门槛，并同时核对成员数、字节数和批次类型。按当前至少 88 批估算，下限为 132 批/分钟；恢复全部 OKX 配对等来源后重新计算，不能固定拿 132 验收更大的负载。

## 第一步 终止慢查询反复叠加

### 现场止损

执行修复时先保持历史导入停止，保留所有 Redis 数据、spool 文件和低频采集状态。如果 Keeper 仍反复超时重启，先暂停该服务的重试来源，再清理已经没有有效调用方等待的 Keeper 只读查询，随后部署修复版。记录暂停与恢复的真实区间，按原有游标补采可恢复的数据。

清理工具必须先输出候选清单：数据库、账户、当前连接 ID、线程 ID、语句摘要、执行时长及调用方状态。执行前再次核对身份，只取消已经确认的本项目过期只读查询；不按“运行超过几秒”批量终止所有 SQL，也不使用报告中记录的旧连接 ID。查询取消后确认其消失；若仍有未完成事务，应由对应调用连接完整回滚。普通 collector 不获得管理员权限。

共享 ClickHouse 的异常合并另行处理。它属于实测环境的一部分，但本方案不依赖停掉其他项目来掩盖新程序自身的问题。

### 给查询本身设置期限

在 `internal/storage/mysql/client.go` 区分生产读、写事务和人工迁移读的超时策略。

| 类型 | 初始策略 |
| --- | --- |
| Keeper 恢复和巡检的普通 SELECT | 服务端执行上限 15 秒，调用 context 20 秒，socket 读等待保留 30 秒 |
| 实时写事务 | 整个尝试上限 40 秒；事务连接的 InnoDB 行锁等待初始 5 秒；任一错误完整回滚 |
| 人工历史读取 | 独立配置、账户和有限上限，不继承到实时 collector |

这些值是首轮测试参数，不是硬件性能承诺。服务端 `max_execution_time` 适用于只读 SELECT，不能把它当作所有 INSERT、锁等待和事务的总时限。[MySQL 执行时限说明](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_max_execution_time)

参数要应用到连接池建立的每条物理连接；不能只在启动时对随机一条池连接执行一次 `SET`。Keeper 遇到超时后进入有上限的指数退避，例如 5、10、20、40、60 秒，加少量抖动，同一任务最多一个在途查询。暂时性存储故障由 runner 有界重试，不能靠 systemd 不断重新启动并重跑全部恢复。

故障测试必须证明：调用方超时或被终止后，服务端对应查询在有限时间内消失，旧查询没有结束时不会再次堆积相同查询。服务端取消不及时的路径需要受控清理机制，不能把断开客户端等同于已取消服务端工作。

### 改写 Keeper 的读取范围

优先检查 `KeeperEvidenceFrontier`，同时复测 `KeeperNextEnrichment`；之前针对 enrichment 的修复不代表 frontier 查询已经优化。

1. 对真实查询条件取得执行计划，记录扫描行数、回表量、排序和耗时。生产只做有界只读检查；会实际执行扫描的分析放到隔离副本。
2. 先查询推进进度所需的 ID、窗口边界和状态，再按主键分批读取必须校验的完整记录。避免在大范围排序时携带整行宽字段。
3. 采用按键继续的分页，初始每页 256 条；不使用越来越大的 OFFSET。相同链窗口的分页和批次必须一起完成核验，页边界不得被当作完整窗口边界；遇到真实缺口停止推进，不能因 LIMIT 截断而越过缺口。
4. 依据计划比较覆盖 `config_hash`、`capture_kind`、`committed`、`status`、`event_kind` 和查询窗口的索引候选。多重范围条件不保证一条索引全部有效，必须用真实数据验证后确定列顺序。索引记录实际新增字节、写入成本和撤销方式，不直接照搬候选列创建宽索引。

完成标准：按原分页完整性规则得到相同进度，查询满足执行期限；持续运行一小时无同类长查询累积，无由该问题引发的进程重启。

## 第二步 让两处积压都有处理机会

### 统一候选批次和调度

修改 `cmd/storage-writer`、`internal/storage/redisbuffer` 和 `internal/storage/spool`。候选任务只包含身份、来源位置、分钟、成员数、字节数和下一次尝试时间；选中后才加载大 payload。

批次唯一身份沿用 `(database, kind, id)`。Redis 和磁盘中的同一批合成一个任务，保留两个来源位置。入库后按同一摘要核验并分别确认两个副本，不能只处理 Redis 后忘记磁盘副本。

按数据年龄而非存储位置分为“最近已封口分钟”和“较早积压”，两组都可来自 Redis 或磁盘：

- 初始将约 70% 处理时间分配给最近两分钟、30% 分配给旧积压；一侧空闲时借用额度。
- 每组内部按 CEX、期权轮转，优先更早的逻辑分钟，避免少量 CEX 批次被大量期权批次长期挡住。
- 使用批次成员数、字节数及近期耗时估计成本；用实际耗时回扣额度，不能简单认为大小批次成本一样。非空旧积压队列必须持续获得调度机会。
- 发生可重试错误的批次独立退避，调度其他可处理批次；不能对所有队列统一睡眠或永远卡在一个队头。内容冲突保留原件并报警，阻断受影响的流或依赖范围；不能悄悄跳过后宣称该范围完整。

如果实时输入持续大于容量，比例调整无法解决问题；必须继续降低单批成本或扩充经过验证的处理能力，不能靠让旧积压永远不动维持“实时正常”。

### 领取和恢复

Redis 的领取必须原子完成“选择可处理候选、检查退避、取得带 owner 的租约”。跳过其他 worker 已领取的批次；不得所有 worker 都先加载同一个队头的大 payload 再抢租约。租约初始 60 秒，每 15 秒续租；释放和续租都要核对 owner。租约失败或 Redis 重启后，MySQL 的批次事务协议仍提供最终防重保证。

采用一个 writer 进程内的有界 worker 池，进程持有专用文件锁，避免误起第二个常驻 writer。进程内按批次身份维护在途表，统一排除 Redis/spool 重复任务；不把进程内去重作为数据库幂等性的替代。

spool 保留现有 `.batch` 格式。启动时分段扫描文件头，重建有界元数据索引；运行时接收新文件通知并定期分段校对，避免每取一批都重新扫描数千个文件。索引是可重建的辅助信息，文件内容和摘要仍是恢复依据。扫描不把全部 payload 读入内存，索引损坏不影响已持久文件。

`spool.Ack` 当前在目录锁内查询 MySQL，应改为先在锁外取得持久提交证明，再持短目录锁核对同一身份和摘要、删除文件并同步目录。不得持目录锁等待数据库或网络；删除前的再次核对必须保留。

完成标准：Redis 持续有数据时，磁盘中的旧批次仍持续完成；重复出现在两处的批次只产生一份逻辑事实；崩溃、租约过期和 ACK 丢失后能够恢复；未入库文件不会被删掉。

## 第三步 减少每批重复工作

### 复用连接和不可变资料

writer 启动时为目标库建立长生命周期连接池，完成 schema 校验并记录版本。每批不再创建、关闭连接池，也不重复查询九张表的 schema hash。连接重建、明确的 schema 变更或周期性低频核对仍需检查兼容性。

复用池不等于共享可变的提交上下文。producer、generation 和 holder 作为每次提交的不可变参数，或绑定到各 worker 的独立会话；不能让并发 worker 对同一个 `Client` 调用 `SetProducer`。缓存返回只读值或副本，避免一个批次修改另一个批次正在验证的对象。

建立有字节上限的元数据缓存，初始 32 MiB，按不可变身份及内容摘要缓存 run、plan、合约定义、规则和证据。对预期哈希不一致、来源首次读取、代次或 schema 版本变化重新核验。不能按交易对名称缓存“最新规则”后用于旧分钟，也不能缓存“没有找到”来永久遗漏随后到达的证据。

把 payload 解码、哈希、静态字段和已持久不可变引用的核验放在事务外准备。一个期权批次中，合约定义只批量读取一次，并复用于 run、盘口与证据校验。按已知规则 ID 批量读取规则，避免逐合约往返数据库。

计划时间边界、唯一性和发布资格仍在事务内复核；准备期间若有效计划发生变化，重新准备或报告冲突。对仍可修订的元数据不适用不可变缓存。不能通过跳过完整性校验获得速度。

### 批量写入与有界准备

盘口差量已有批量实现，优先把 `options_catalog_quality_evidence_minute` 的逐行检查和插入改成同样有界的批量路径；低频存在相同热点时再按其模型逐项改造。

每批 SQL 初始最多 500 行、8 MiB 参数数据，保持键冲突、完整字段摘要和历史 multiplicity 的检查。超出字节上限时按字节二分或分块，不能退化成整组逐条写。不要使用覆盖式 upsert 消除冲突。

准备任务初始 2 个，准备队列和缓存按字节限额管理；初始准备预算 64 MiB，计入解码对象及待提交记录，不能只数压缩 payload。超过预算的单批采用有界分块准备，保留同一最终事务和提交身份。内存预算需用代表性活跃、非活跃和极端换价样本验证。

第一阶段仍用 1 个数据库提交 worker，先确认重复读和逐条写减少后带来的收益，再启用下一节的双 worker。每阶段分别保留相同负载的前后数据。

## 第四步 缩短事务并允许安全并发

### 区分业务互斥和进程代次

现有 `Client.transaction` 对所有同一 service 的事务使用 `FOR UPDATE`。不能把这个函数统一替换成共享锁：身份分配、计划发布、发现事实、DEX 修订等路径仍可能依赖串行化。

为已封口的 CEX、期权分钟增加专用提交路径：

- 不可变分钟提交在事务内对同一 `producer_generation` 行取得 `FOR SHARE`，核对 generation 和 holder，持锁直到提交或回滚。
- `ActivateProducer` 保持 `FOR UPDATE`。它等待已有分钟事务结束后才能变更代次；变更后旧进程不能开始新的合法提交。
- 现有元数据、计划发布和其他可变业务继续使用独占路径。本轮不顺带解除它们的业务锁；长元数据事务应分开优化。
- `writeSlot` 不再无条件串行化整个分钟连接池。只有通过完整测试的不可变分钟走并发路径，其他调用保持原行为。

共享锁可并存，并阻止对被锁行的修改；锁持有到事务结束。这是代次保护的基础，不能改成事务外检查一次 generation。[MySQL 锁定读取说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

### 用已有提交表防止重复执行

不新增一个常驻“通用任务事实表”。复用 `cmi_storage.ingest_batch` 的现有唯一键，在**同一个 InnoDB 事务**中提前占住批次身份，最后才提交：

```text
事务外准备并校验 payload 和不可变引用
BEGIN
  共享锁定并核对 producer generation 与 holder
  INSERT ingest_batch 的完整身份和摘要
  复核分钟有效计划与发布条件
  批量检查并写入事实 成员和领域提交记录
  将本事务中新插入行的 committed_at 更新为提交前的 UTC 时间
COMMIT
事务成功后再次取得持久提交证明
确认 Redis 和磁盘中的对应副本
```

提前插入的提交行在事务完成前对其他连接不可见；失败时事实和提交行一起回滚。外部健康检查、迁移工具和查询必须使用已提交读，不能启用 `READ UNCOMMITTED`。`committed_at` 仍表示提交前记录的时间，不充当精确的物理落盘结束时间；后者由提交成功后的指标记录。

并发相同批次遇到唯一键冲突时，回滚本次事务，再读已经提交的记录，对比 database、kind、id、service、generation、logical_time、codec、成员数和内容摘要。完全一致才确认副本，不一致返回冲突并保留队列。不得修改既有提交行来适配不同内容，也不得把普通事实表的任意重复键错误当成整批成功。原 `Committed` 检查仍可在开始前快速识别已经完成的批次，包括已经完成的旧代次批次。

此路径直接利用已存在的表和实时账户对 `ingest_batch` 的权限，不需要新增批次表。实施后同步更新 `docs/market-data-storage.md` 的提交时序说明。

同步替换 CEX、`options_live` 和 `options_catalog` 原来在事务末尾插入提交行的逻辑，避免提前占位后再次 INSERT。完成时间 UPDATE 只允许作用于本事务刚插入的行；已经存在的成功提交只核验和确认，不改时间、摘要或身份。

### 并发和错误处理

先启用 **2 个提交 worker**，不直接多开进程。相同批次的 Redis 租约、进程内在途表和 MySQL 唯一键分别提供领取、去重和最终事务保护。统一表及主键操作顺序，降低重叠引用造成的死锁概率。

提交池初始最多 2 条事务连接；准备读取最多 2 条连接。总数 4 条计入现有实时账户 16 条总配额，实施前按主 collector 和四个低频进程逐项核算并为恢复留余量。必要时收敛已有各池上限，不通过给每个 worker 都配置大连接池解决。CPU、内存和 I/O 同步测量后才考虑更多并发。

死锁、锁等待超时和断线都完整回滚或按“结果未知”处理，再查询持久提交记录，保留同一批次身份有界重试。锁等待超时并不保证整个事务已经回滚，应用必须显式结束事务，不能带着部分成功继续提交。[MySQL 事务错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

40 秒是应用尝试期限，不证明断线后的服务端写事务已经结束。记录该尝试的连接和事务身份；无法确认回滚时保留原批次，检查持久提交与服务端事务状态。清理遗留写事务必须重新核对连接归属和本次尝试，确认回滚完成后才释放其资源；不能把“客户端返回超时”直接计为“事务已取消”。

Redis 失败、ACK 失败或租约丢失均不能作为删除磁盘文件的依据。发生已确认内容冲突时保留原件，明确受影响范围和错误状态。

## 监控和容量控制

每 10 秒输出轻量聚合指标，避免为监控扫描全部历史或打印每行数据：

| 指标 | 用途 |
| --- | --- |
| 新封口批次和成员数 字节数 每分钟提交数 | 比较真实生产和消费速度 |
| Redis 与 spool 各自数量 字节 最老逻辑分钟 | 防止只看 Redis 得出已排空的错误结论 |
| 按身份去重的未提交量 和 已提交待清理量 | 区分真正积压与 ACK 清理滞后 |
| 最近数据与旧积压分别获得的处理时间 | 验证调度公平性 |
| 排队 准备 取锁 SQL 提交 ACK 各阶段耗时 | 定位改善来源，不能把等待都算作 MySQL 写入时间 |
| 长查询数 孤立查询数 重启数 行锁等待 | 验证 Keeper 和事务修复 |
| CPU RSS swap 磁盘吞吐及忙碌时间 | 验证增并发没有把瓶颈转成内存和磁盘压力 |

沿用 20 GiB spool 上限。初始达到 50% 报警，75% 强报警并保持历史导入停止；按近期净增长估算剩余可写时间，同时检查根盘空间。额度达到上限时按既有持久交付协议明确失败，不能删除未提交数据或假装接纳成功。Redis 仍使用 `noeviction`，保留 AOF、封口持久确认和 MySQL 原有提交持久化设置。

清空积压的时间用 `去重待写量 / 实测净消化速度` 估算；净消化速度不为正时不报完成日期。批次大小差异大时同时给出字节和处理时间口径。不能凭 Redis 变小或 writer 仍存活宣布恢复。

## 验收标准

### 正确性和故障恢复

必须使用与生产相同持久化配置的隔离 MySQL、Redis，至少覆盖：

1. Redis 和 spool 同一批重复出现、两 worker 同时领取、租约到期、Redis 重启；最终逻辑事实相同且两处副本能够确认。
2. 事务占位后、事实写到一半、COMMIT 前后、ACK 前后分别终止 worker；不能留下可见的半批次或提前清理文件。
3. 同身份不同内容仍报冲突；普通唯一键冲突不被当成整批成功。死锁和锁等待超时后事务没有残留。
4. 双分钟提交期间切换 generation，旧代事务与新代激活的先后关系可证明；新代激活后旧进程不能继续提交未完成新批次。
5. 分钟提交与计划发布、规则更新、身份分配同时发生，保留原发布顺序与首次已知时间语义。
6. 缓存冷启动、淘汰、失效和 schema 不匹配；校验结果与不使用缓存时一致。
7. Keeper 分页边界落在同一链窗口中间、存在缺页、父子批次不完整及来源失败，均不得错误推进进度。
8. 按项目 AGENTS 要求完整回放新 5/10 档、旧 10/50 档及混合历史；验证同秒最终值、零数量删除、无变化与无效秒、断档、重组和最终性。

### 性能和运行验收

- 使用完整覆盖的冻结真实样本连续回放至少 60 分钟，保持原订阅范围、采样频率及质量规则；包括活跃、非活跃流和全档换价压力样本。不能只测 INSERT，必须包含全部引用核验、持久化、ACK 和队列恢复。
- 有积压时持续处理能力达到至少 `1.5 × R`，最近数据按时提交，去重后的旧数据数量和字节持续下降，最老逻辑分钟持续前移。追赶初期最老等待时长仍可能增加，因此不能单凭年龄判断是否在消化积压。坏批次单独披露，不能算进已排空。
- 排空后，新分钟最后一批在封口后 30 秒内完成的 P99 达标，正常待写少于两分钟。Redis、spool 和低频 pending 都检查，不能漏掉一处。
- 连续 24 小时验证无吞吐导致的持续积压反弹、无同类长查询和重启循环；同时测量每日表数据、索引、AOF、binlog、spool 空间和代表性回放耗时。
- 实时稳定并有容量余量后，再以单 worker、小块方式恢复历史迁移。实时提交延迟达到 30 秒先降速，达到 60 秒停止接纳新历史块，正在执行的有界事务正常结束。

60 分钟回放和现场短窗口通过可以先报告阶段性恢复；24 小时持续验收完成后再宣布稳定。达不到目标时按阶段耗时继续定位，不降低数据质量门槛。

## 部署和回滚

保存实际源码状态、候选二进制哈希、旧二进制、配置和 schema 版本。工作区已有其他改动，不能覆盖或回退整个仓库。

先修 Keeper，后切 writer。更新 writer 时停止旧 writer 并确认退出，采集器继续按原协议持久交付，再启动新 writer 读取原队列。单独更新 writer 不激活新的 collector generation；旧积压仍使用原身份。若确实必须切换 producer 代次，须先按既有恢复协议解决旧代未提交批次，不能修改文件中的代次或摘要来强行提交。

上线先以一个提交 worker 核对正确性，再开启两个；任一阶段出现新的数据冲突、回放差异或资源异常，先恢复单 worker，保留全部队列。需要回退程序时等待在途事务结束或确认回滚，再换回兼容原文件格式的上一版本；不把旧程序无法读取的新队列格式留在现场。

索引回滚与程序回滚分开进行，不在紧急回退时盲目执行大表重建。所有历史和已接纳批次继续保留，回滚不能撤销已经成功入库的新事实。
