# ARB-0002 结算窗口数据采集规则

> 迁移说明：本文件来自 `crypto-arb-observer`，完整保留其 T-5 至 T+2 专项窗口方案。本项目当前采用持续秒级盘口采样，并未因迁入本文而切换为该窗口方案；当前实现以 [`../../implementation-design.md`](../../implementation-design.md) 为准。

状态：用户已确认的目标业务规则

范围：Binance与OKX同名USDT永续合约的funding结算窗口数据采集、top1/top100选择和窗口间状态

不包含：机会事件生命周期、下单、账户、仓位、API Key和实盘风控

本文是来源项目 ARB-0002 结算窗口数据采集的业务主源。涉及来源项目的结算窗口、T-5预热、top1/top100选择和135点正式采样时，以本文为准。其实现状态应以 `crypto-arb-observer/docs/ai/current-state.md` 和来源项目实际代码为准。

## 1. 交易对匹配

- Binance和OKX按同名币种直接匹配。
- 默认认为同名永续合约是同一个标的。
- 后续发现某个币匹配错误时，删除错误数据，并将交易对加入例外名单。
- 不预先建设复杂的合约身份验证。

## 2. 结算窗口生成

对每个两边都有的交易对：

- 只要Binance或OKX任意一边在时间`T`结算funding，就为这个币生成一个`T`窗口。
- 即使另一边在`T`不结算，也必须采集另一边当时的数据。
- 如果两边都在同一个`T`结算，只生成一个窗口，不重复采集。
- 不同结算时间分别生成窗口。

例如，OKX在08:00结算、Binance在12:00结算：

- 08:00窗口采集OKX和Binance双方数据。
- 12:00窗口再次采集双方数据。

## 3. 窗口时间范围

每个`T`窗口分为预热和正式采样两个阶段。

### 3.1 T-5分钟：选择和预热

在`T-5`：

1. 获取双方当前funding rate。
2. 计算双方funding差。
3. 根据上一窗口的盘口状态，执行进入规则或维持规则。
4. 确定本窗口每个币使用top1还是top100。
5. 启动对应盘口订阅。
6. top100在这一阶段完成预热。

`T-5`到`T-3`主要用于盘口启动和top100预热，不属于135个正式采样点。

### 3.2 T-3分钟到T+2分钟：正式采样

- 严格按照预定的135个时间点采集。
- 每个时间点同时获取并保存Binance和OKX的数据。
- `T`本身必须是正式采样点之一。
- 本窗口选定的盘口深度保持不变，中途不重新判断。

即使funding差在`T`附近突然跨过阈值：

- 本窗口也不临时从top1升级到top100。
- 仍然保存当时的funding、mark price和top1。
- 接受少量这种情况的数据不完整。

## 4. 盘口状态

数据采集层只有两种状态：

- `top1`
- `top100`

数据采集层不再使用`candidate`或`active`状态。

每个币保存上一窗口最终选择的盘口状态。在新的`T-5`：

- 上一窗口为top1：使用进入规则判断。
- 上一窗口为top100：使用维持规则判断。
- 第一次出现、没有历史状态：按top1状态处理，使用进入规则。

这个状态只用于决定下一个窗口采用哪条规则，并不表示窗口之间还在持续抓盘口。

## 5. top100筛选

对同一个`T`即将采样的所有交易对：

1. top1状态的币执行进入规则。
2. top100状态的币执行维持规则。
3. 将所有判断通过的币放入同一个列表。
4. 按当前funding差从大到小排序。
5. 只取前`K`个使用top100。
6. 其余币使用top1。

其中：

- `K`是可配置参数，初始默认值为20，后续可以修改。
- `K`限制的是交易对数量；一个top100交易对会同时占用Binance和OKX各一个top100目标。
- 原top100币没有保留名额的绝对优先权。
- 维持规则只决定原top100币是否有资格进入排序。
- 最终排名仍然由当前funding差决定。
- funding差按照两个站点较高费率减去较低费率计算，同时可以由此确定潜在多空方向。

进入规则和维持规则的具体阈值使用各自独立配置；本文只固定它们的调用时机和排序方式。

## 6. 盘口订阅方式

- 使用top1的币，两边都抓top1。
- 使用top100的币，两边都抓top100。
- top100已经包含最优买卖价，不再为同一个币同时保留一套重复的top1订阅。
- 深度选择以交易对为单位，不允许一边top1、另一边top100。

## 7. 每个正式采样点保存的数据

每个交易所分别保存：

- funding rate。
- funding rate对应的`next funding time`。
- mark price。
- order book。
- 本窗口选择的盘口深度：top1或top100。
- 交易所返回的数据时间。
- 本地实际接收时间。

采样记录还需要保存：

- 交易对。
- 窗口中心时间`T`。
- 当前采样点相对`T`的偏移。
- 哪个交易所在`T`结算；如果双方都结算，则记录双方。

这些字段用于判断`T`前后的funding rate属于哪个结算周期。

如果某个时间点的某个站点获取失败：

- 记录该字段缺失。
- 不伪造数据。
- 不补抓过去的盘口。
- 不因为单点失败改变本窗口的盘口深度。

## 8. T+2之后

窗口结束后：

1. 停止本窗口的所有top1和top100盘口订阅。
2. 不再继续抓funding、mark price和盘口。
3. 保存每个币本窗口选定的top1/top100逻辑状态。
4. 使用`T`之后采集到的`next funding time`安排下一次窗口。

例如08:00窗口选择了top100：

- 08:02后停止真实top100订阅。
- 只保留“上一窗口是top100”这个状态。
- 到12:00窗口的`T-5`，再使用维持规则重新判断。

## 9. 窗口外行为

窗口外不持续采集：

- funding rate。
- mark price。
- top1。
- top100。

程序只需要：

- 启动时获取一次各币的`next funding time`。
- 后续使用每个窗口内已经采集到的新`next funding time`安排下一窗口。

如果交易所在窗口之间临时修改结算时间，系统可能漏掉一次窗口。当前接受这个风险，实际发生后再考虑增加低频时间表刷新。

## 10. 完整数据流

```text
程序启动
→ 按同名币种匹配Binance和OKX
→ 获取next funding time
→ 找到任意一边的结算时间T

T-5
→ 获取双方funding
→ 上次top1则执行进入规则
→ 上次top100则执行维持规则
→ 所有通过者按funding差排序
→ 前K个选择top100，其余选择top1
→ 启动并预热盘口

T-3到T+2
→ 在135个预定时间点
→ 同时保存双方funding、next funding time、mark price和盘口
→ 本窗口不再切换盘口深度

T+2
→ 停止所有盘口订阅
→ 保存本窗口top1/top100状态
→ 根据新next funding time安排下一窗口
```

机会识别、收益计算和历史分析以后基于这些数据单独完成，不再反过来控制采集流程。
